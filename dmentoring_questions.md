01Есть ли аналог try-catch в Go?
Middle
Go
Go не имеет исключений — вместо них используется **явный возврат ошибки** как второго значения.
Паттерн error handling:
```
result, err := someFunc()
if err != nil {
    return nil, fmt.Errorf("someFunc: %w", err)
}
```
Для **паники** (аналог unrecoverable exception) существует `recover`:
```
func safeRun() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    mightPanic()
    return nil
}
```
**recover** работает только внутри `defer` и только в той же горутине. Паники следует использовать для программных ошибок (индекс за пределами, nil pointer), а не для обычного control flow. Для бизнес-ошибок всегда возвращайте `error`.
02Как передаются аргументы в Go, по значению или по ссылке?
Middle
Go
В Go **все аргументы передаются по значению** — функция получает копию.
Что это означает на практике:
- **int, bool, float, struct** — копируется полностью, оригинал не меняется  
- **pointer** (`*T`) — копируется указатель, но он указывает на ту же память, поэтому через него можно изменить оригинал  
- **slice** — копируется заголовок (ptr + len + cap), но underlying array общий. Элементы можно менять, а `append` снаружи не виден  
- **map, channel** — передаётся ссылка на внутреннюю структуру, изменения видны снаружи  
- **interface** — копируется пара (тип + указатель на данные)
Пример:
```
func addElem(s []int) {
    s = append(s, 99) // не видно снаружи
    s[0] = 999        // видно снаружи
}
```
Если нужно изменить переменную — передавайте указатель `*T` или возвращайте новое значение.
03Что будет при чтении/записи в nil channel?
Middle
Go
**nil channel** — это channel, объявленный но не инициализированный (`var ch chan int`).
**Поведение:**
**Отправка в nil channel** — блокируется навсегда.
**Чтение из nil channel** — блокируется навсегда.
**`close(nil channel)`** — **panic**.
Это поведение используется в паттерне **отключения case в select**:
```
func merge(a, b <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        for a != nil || b != nil {
            select {
            case v, ok := <-a:
                if !ok { a = nil; continue }
                out <- v
            case v, ok := <-b:
                if !ok { b = nil; continue }
                out <- v
            }
        }
        close(out)
    }()
    return out
}
```
Когда канал закрывается, его приравнивают к `nil` — и `select` перестаёт его выбирать. Таким образом nil channel — **не ошибка, а инструмент управления concurrency**.
04Что такое nil interface?
Middle
Go
Interface в Go внутри хранит **пару: (тип, значение)**. Interface равен `nil` только тогда, когда **оба поля nil**.
Например:
```
func getError() error {
    var p *MyError = nil
    return p  // возвращает НЕ nil!
}
err := getError()
fmt.Println(err == nil) // false!
```
Здесь `err` имеет тип `*MyError` (не nil) и значение `nil` — поэтому интерфейс не nil.
Правильно:
```
func getError() error {
    var p *MyError = nil
    if p == nil {
        return nil  // явно возвращаем nil interface
    }
    return p
}
```
**Проверка типа и значения:**
```
var i interface{} = (*int)(nil)
fmt.Println(i == nil)          // false — тип есть
fmt.Println(i.(*int) == nil)   // true  — значение nil
```
Это одна из самых частых причин ошибок при работе с `error` в Go.
05Какие типы можно использовать как ключи в map?
Middle
Go
Ключом в map может быть любой **comparable** тип — тот, для которого определён оператор `==`.
**Можно:**  
- Числа: `int`, `float64`, `uint`, и т.д.  
- `string`  
- `bool`  
- Указатели (`*T`) — сравниваются по адресу  
- Структуры, **все поля которых comparable**  
- Массивы (`[N]T`) если `T` comparable  
- Интерфейсы (с осторожностью — panic если динамический тип не comparable)
**Нельзя:**  
- `slice` — не comparable  
- `map` — не comparable  
- `func` — не comparable
Пример со структурой как ключом:
```
type Point struct{ X, Y int }
m := map[Point]string{
    {1, 2}: "A",
    {3, 4}: "B",
}
fmt.Println(m[Point{1, 2}]) // "A"
```
Это полезно для кэширования результатов по составному ключу без конкатенации строк.
06Сколько памяти выделится при передаче строки 1MB в функцию?
Middle
Go
В Go строка (`string`) внутри — это **заголовок из двух полей**: указатель на данные + длина. Размер заголовка — **16 байт** на 64-битной системе.
При передаче строки в функцию копируется только этот заголовок — **16 байт**, а не сам контент.
```
func process(s string) {
    // s — копия заголовка (16 байт)
    // underlying данные те же, не копируются
    fmt.Println(len(s))
}
big := strings.Repeat("x", 1_000_000)
process(big) // 16 байт, не 1MB
```
Строки в Go **иммутабельны** — поэтому безопасно делиться underlying массивом без копирования.
**Когда данные реально копируются:**  
- `[]byte(s)` — создаёт новый буфер с копией содержимого  
- конкатенация строк через `+` — аллоцирует новую память  
- `strings.Builder` или `bytes.Buffer` — для эффективного построения строк
Вывод: передача даже больших строк в функцию дешёвая — O(1) по памяти.
07Что такое модули в Go? Как они улучшают управление зависимостями?
Middle
Go
**Go модули** — система управления зависимостями, введённая в Go 1.11 и ставшая дефолтной в Go 1.16.
Модуль определяется файлом `go.mod` в корне проекта:
```
module github.com/mycompany/myapp
go 1.22
require (
    github.com/gin-gonic/gin v1.9.1
    github.com/lib/pq v1.10.9
)
```
**Что даёт система модулей:**
- **Воспроизводимые сборки** — `go.sum` содержит хеши всех зависимостей, гарантируя целостность  
- **Версионирование** — зависимости фиксируются по semver (`v1.9.1`)  
- **Поддержка нескольких мажорных версий** — `github.com/lib/v2` и `v1` могут сосуществовать  
- **Прокси** — по умолчанию загрузка через `proxy.golang.org`, что ускоряет и кэширует  
- **Vendor** — `go mod vendor` копирует зависимости локально для оффлайн-сборки
**Основные команды:**
```
go mod init github.com/myapp   # создать модуль
go get github.com/pkg@v1.2.3   # добавить зависимость
go mod tidy                    # убрать лишнее, добавить нужное
go mod download                # скачать все зависимости
```
До модулей использовался GOPATH — все проекты жили в одной директории, версионирование было сложным.
08Что такое stop-the-world?
Middle
Go
**Stop-the-world (STW)** — это паузы в выполнении программы, когда Go runtime останавливает все горутины для выполнения служебных операций.
**Когда происходит STW:**  
- Фазы сборки мусора (GC), требующие консистентного вида heap  
- Изменение размера heap  
- Горутина создаёт стек и нужна синхронизация
**Эволюция GC в Go:**  
- Go 1.4 и раньше: долгие STW паузы (десятки мс)  
- Go 1.5+: конкурентный трёхцветный mark-and-sweep — большинство работы без STW  
- Сегодня: STW паузы обычно **< 1 мс**, часто 100–200 мкс
**Что происходит во время STW:**
```
[программа работает] → STW → [GC делает scan roots] → программа продолжается
                       ^^^
                    все горутины остановлены
```
**Как уменьшить влияние:**  
- Уменьшить количество аллокаций (sync.Pool, prealloc)  
- Тюнинг `GOGC` (по умолчанию 100 — GC при удвоении heap)  
- `GOMEMLIMIT` — лимит памяти вместо агрессивного GOGC  
- Использовать `runtime/trace` и `pprof` для анализа пауз
STW — компромисс: управляемая память vs небольшие паузы. В Go он минимизирован настолько, что большинство сервисов его не замечают.

10Как профилировали Go-приложение? Какие проблемы можно найти при профилировании?
Middle
Go
**Инструменты профилирования в Go:**
Встроенная поддержка через `net/http/pprof`:
```
import _ "net/http/pprof"
// http://localhost:6060/debug/pprof/
```
**Типы профилей:**  
- **CPU** — где приложение тратит время (`/debug/pprof/profile?seconds=30`)  
- **Heap** — аллокации памяти, что живёт в heap (`/debug/pprof/heap`)  
- **Goroutine** — список всех горутин и их стеки (`/debug/pprof/goroutine`)  
- **Block** — блокировки на channel/mutex (`/debug/pprof/block`)  
- **Mutex** — конкуренция за mutex (`/debug/pprof/mutex`)  
- **Trace** — полный trace событий (`/debug/pprof/trace`)
**Команды для анализа:**
```
go tool pprof http://localhost:6060/debug/pprof/heap
(pprof) top10        # топ потребителей
(pprof) web          # граф в браузере
(pprof) list myFunc  # строчный breakdown функции
```
**Типичные проблемы которые находили:**  
- **Memory leak** — горутины держат ссылки, heap растёт бесконечно  
- **Goroutine leak** — goroutine stack в profiler растёт, горутины не завершаются  
- **Hot path** — одна функция занимает 80% CPU (часто JSON marshal, regexp)  
- **Excessive allocations** — много мелких аллокаций → частый GC  
- **Lock contention** — mutex блокирует параллельные горутины
**Race detector:**
```
go test -race ./...
go run -race main.go
```
Находит data race — одновременную запись/чтение без синхронизации.
11Чем опасен time.After (или таймер) в цикле?
Middle
Go
`time.After(d)` создаёт **новый канал и таймер** при каждом вызове. Если вызывать его в цикле, таймеры не освобождаются до истечения времени — это **memory leak**.
Пример проблемы:
```
for {
    select {
    case msg := <-ch:
        process(msg)
    case <-time.After(5 * time.Second): // новый таймер на каждой итерации!
        log.Println("timeout")
    }
}
```
При высоком темпе сообщений таймеры накапливаются в памяти — каждый живёт 5 секунд и не GC-ится раньше срока.
**Правильное решение — переиспользовать таймер:**
```
timer := time.NewTimer(5 * time.Second)
defer timer.Stop()
for {
    timer.Reset(5 * time.Second)
    select {
    case msg := <-ch:
        process(msg)
    case <-timer.C:
        log.Println("timeout")
    }
}
```
**Или через context с таймаутом:**
```
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
select {
case msg := <-ch:
    process(msg)
case <-ctx.Done():
    log.Println("timeout")
}
```
Правило: `time.After` безопасен для одноразового использования, но не в tight loop.
12Почему context нельзя хранить в структуре и переиспользовать?
Middle
Go
По соглашению Go, `context` — **параметр запроса**, а не поле структуры. Это зафиксировано в официальном руководстве: «Do not store Contexts inside a struct type».
**Почему нельзя хранить в структуре:**  
- Context несёт дедлайн и cancellation конкретного **вызова**, а не объекта  
- Если сохранить ctx в структуре, он «проживёт» дольше нужного — отмена не сработает вовремя  
- Переиспользование ctx из другого запроса может отменить текущий или наоборот
```
// Плохо
type Service struct {
    ctx context.Context // нельзя!
}
// Правильно
func (s *Service) DoWork(ctx context.Context) error {
    return s.repo.Fetch(ctx, ...)
}
```
**Исключения:** допустимо хранить ctx в структуре, если она сама является единицей жизни запроса (например, кастомный `http.Request`-обёртка), но это редкий кейс.
**Правило:** ctx всегда первым параметром функции, всегда передаётся явно — это делает границы отмены очевидными.
13Почему сравнение ошибок через == — плохая практика?
Middle
Go
Оператор `==` сравнивает ошибки **по идентичности указателя**, а не по смыслу. Это ломается при **оборачивании** ошибок через `fmt.Errorf("%w", err)`.
Пример проблемы:
```
var ErrNotFound = errors.New("not found")
func getUser(id int) error {
    return fmt.Errorf("getUser: %w", ErrNotFound) // обёрнутая ошибка
}
err := getUser(42)
fmt.Println(err == ErrNotFound)          // false! разные указатели
fmt.Println(errors.Is(err, ErrNotFound)) // true  — правильно
```
**Правильный подход:**
- `errors.Is(err, target)` — рекурсивно разворачивает цепочку оборачиваний, проверяет каждый уровень  
- `errors.As(err, &target)` — проверяет тип ошибки и извлекает её значение
```
var notFound *NotFoundError
if errors.As(err, &notFound) {
    fmt.Println("id:", notFound.ID)
}
```
**Исключение:** сравнение с `nil` через `==` абсолютно корректно:
```
if err != nil { ... } // всегда правильно
```
14В чем разница между panic и error?
Middle
Go
**error** — штатный механизм обработки ошибок в Go. Это значение, которое функция возвращает явно.
```
func divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("division by zero")
    }
    return a / b, nil
}
```
**panic** — аварийное завершение горутины. Runtime разворачивает стек, выполняет все `defer`, затем завершает программу (если нет `recover`).
```
func mustOpen(path string) *os.File {
    f, err := os.Open(path)
    if err != nil {
        panic(err) // программная ошибка — файл обязан существовать
    }
    return f
}
```
Если вызывающий код может разумно обработать ситуацию — возвращайте `error`. Если ситуация означает баг в программе и продолжать бессмысленно — `panic`. Публичные API никогда не должны паниковать без крайней необходимости.
15Расскажи что такое SOLID?
Middle
Go
SOLID — пять принципов объектно-ориентированного дизайна, делающих код гибким и поддерживаемым.
**S — Single Responsibility:** каждый модуль/тип отвечает за одну вещь.
**O — Open/Closed:** открыт для расширения, закрыт для изменения. В Go — через интерфейсы: добавляй новые реализации, не трогая существующий код.
**L — Liskov Substitution:** реализации интерфейса должны быть взаимозаменяемы. Если `MockRepo` ведёт себя иначе, чем `PostgresRepo` — нарушение.
**I — Interface Segregation:** маленькие интерфейсы лучше больших. В Go это идиоматично — интерфейс на 1–2 метода норма:
```
type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }
```
**D — Dependency Inversion:** зависеть от абстракций (интерфейсов), а не от конкретных типов. Передавай `UserRepo` как интерфейс, а не `*PostgresUserRepo`.
16Что такое принципы KISS? DRY?
Middle
Go
**KISS (Keep It Simple, Stupid)** — решение должно быть максимально простым. Сложность должна быть оправдана реальной необходимостью, а не предвосхищением будущего.
```
// Плохо: преждевременная абстракция
type StrategyFactory interface { Create() Strategy }
// Хорошо: просто функция
func processPayment(amount int) error { ... }
```
**DRY (Dont Repeat Yourself)** — каждая часть знания должна иметь единственное представление в системе. Дублирование — источник багов: правишь в одном месте, забываешь в другом.
```
// Плохо: одна валидация в двух местах
// Хорошо: вынести в функцию
func validateAge(age int) error {
    if age < 0 || age > 150 { return errors.New("invalid age") }
    return nil
}
```
**Важный баланс:** DRY не означает «никогда не повторять код». Иногда 2–3 похожих строки лучше преждевременной абстракции — WET (Write Everything Twice) допустим для маленьких дублирований.
17Что такое DI? Как у вас решено внедрение зависимостей?
Middle
Go
**DI (Dependency Injection)** — паттерн, при котором зависимости передаются в объект снаружи, а не создаются внутри. Это упрощает тестирование и снижает связность.
**В Go DI делается через интерфейсы и конструкторы:**
```
type UserRepo interface {
    GetByID(ctx context.Context, id int) (*User, error)
}
type UserService struct {
    repo UserRepo // зависимость — интерфейс, не конкретный тип
}
func NewUserService(repo UserRepo) *UserService {
    return &UserService{repo: repo}
}
```
**В тестах подменяем реализацию:**
```
type mockRepo struct{}
func (m *mockRepo) GetByID(...) (*User, error) { ... }
svc := NewUserService(&mockRepo{})
```
**Способы организации в проекте:**  
- **Вручную** в `main.go` — просто и прозрачно, подходит для большинства сервисов  
- **Wire** (google/wire) — кодогенерация графа зависимостей  
- **fx** (uber-go/fx) — рефлекшн-based контейнер с lifecycle-хуками

19В чем разница между массивом и срезом?
Middle
Go
**Массив** — фиксированного размера, тип включает длину: `[3]int` и `[4]int` — разные типы. Передаётся по значению (копируется целиком).
**Срез (slice)** — динамический вид на массив. Внутри три поля: указатель на массив, длина (`len`) и ёмкость (`cap`).
```
arr := [3]int{1, 2, 3}   // массив
s := []int{1, 2, 3}      // срез
s2 := arr[0:2]           // срез поверх массива
```
На практике массивы используют редко — только когда размер известен заранее и важна семантика значения. В остальных случаях — срезы.
20Как работает append и какие могут быть подводные камни?
Middle
Go
`append` добавляет элементы в срез. Если `cap` достаточно — добавляет на месте. Если нет — **выделяет новый массив** (обычно удваивает ёмкость) и копирует данные.
```
s := make([]int, 3, 4) // len=3, cap=4
s = append(s, 1)       // cap хватает, тот же массив
s = append(s, 2)       // cap не хватает — новый массив!
```
**Подводные камни:**
**1. Срез после append может не разделять память с оригиналом:**
```
a := []int{1, 2, 3}
b := append(a, 4) // если был реаллок — b и a независимы
a[0] = 99
fmt.Println(b[0]) // может быть 1, не 99
```
**2. Неожиданное изменение оригинала:**
```
a := make([]int, 2, 5)
b := a[1:3]
b = append(b, 7)
fmt.Println(a) // [0 0 7] — a изменился!
```
**3. Частые реаллоки при неизвестном размере** — используй `make([]T, 0, expectedSize)`.
Всегда присваивай результат `append` обратно: `s = append(s, v)`.

22Как устроена map? Какие алгоритические сложности у операций?
Middle
Go
**Старая мапа до 1.24:**
**Map** в Go реализована как хэш-таблица с открытой адресацией на основе бакетов. Каждый бакет хранит до 8 пар ключ-значение. При заполнении выше ~6.5 элементов на бакет происходит инкрементальный рехэш.
**Алгоритмические сложности:**
**Get** — в среднем O(1), в худшем O(n).
**Set** — в среднем O(1), в худшем O(n).
**Delete** — в среднем O(1), в худшем O(n).
Худший случай — много коллизий (маловероятно с хорошим хэшером).
**Важные особенности:**
**Порядок итерации случаен** — намеренно рандомизирован в Go.
**Map не потокобезопасна** — нужен `sync.Mutex` или `sync.Map`.
**Zero value map** — `nil`; читать можно, писать — паника:
```
var m map[string]int
_ = m["key"] // ok, вернёт 0
m["key"] = 1  // panic: assignment to entry in nil map
```
**Проверка наличия ключа**: `v, ok := m[key]`.
**После многих удалений память не освобождается** — бакеты остаются; для освобождения нужно пересоздать map.
**Новая мапа после 1.24:**
Начиная с **Go 1.24**, встроенная `map` заменена на реализацию на основе **Swiss Tables** без изменений клиентского апи.
**Swiss Table** — хэш-таблица с закрытой адресацией (open addressing) и линейным пробированием. Данные хранятся в **группах по 8 слотов**, каждая группа имеет 64-битное **контрольное слово** (control word). Каждый байт контрольного слова хранит 7 бит хэша ключа (H2), что позволяет за одну операцию сравнить хэш сразу с 8 слотами параллельно — на amd64 это делается через **SIMD-инструкции**.
**Алгоритмические сложности** остались прежними:
**Get** — в среднем O(1), в худшем O(n).
**Set** — в среднем O(1), в худшем O(n).
**Delete** — в среднем O(1), в худшем O(n).
**Ключевые отличия от старой реализации:**
**Нет overflow-бакетов** — вместо цепочек используется линейное пробирование. Более cache-friendly, так как данные лежат в непрерывной памяти.
**Выше load factor** — 87.5% вместо 81.25%. Это означает меньший расход памяти при том же количестве элементов.
**Производительность** — бенчмарки показывают ускорение **20–50%** на операциях чтения и вставки, особенно на больших map. Итерация быстрее на **50–60%**.
**Всё остальное не изменилось**: порядок итерации по-прежнему рандомизирован, map не потокобезопасна, zero value — `nil`, проверка ключа через `v, ok := m[key]`.
23Что такое пустой интерфейс? Чем отличается от any?
Middle
Go
`interface{}` и `any` — **одно и то же**. `any` — алиас, введённый в Go 1.18 для читаемости.
```
var a any = 42
var b interface{} = 42
// a и b идентичны по типу
```
**Пустой интерфейс** не имеет методов — ему удовлетворяет любой тип. Используется когда тип заранее неизвестен.
**Внутреннее устройство:** два указателя — на **тип** и на **значение**.
```
func Print(v any) {
    fmt.Println(v) // работает с любым типом
}
```
**Как достать значение обратно — type assertion:**
```
var v any = "hello"
s, ok := v.(string) // ok=true, s="hello"
n, ok := v.(int)    // ok=false, n=0
```

```
switch t := v.(type) {
case string:  fmt.Println("string:", t)
case int:     fmt.Println("int:", t)
}
```
**Когда использовать:** для обобщённых контейнеров или API, где тип неизвестен. В новом коде предпочитай дженерики вместо `any` — они типобезопасны.
24Что делает оператор select и для чего он нужен?
Middle
Go
`select` позволяет горутине **ждать сразу несколько канальных операций** и выполнить ту, что готова первой.
```
select {
case msg := <-ch1:
    fmt.Println("ch1:", msg)
case ch2 <- value:
    fmt.Println("sent to ch2")
case <-time.After(1 * time.Second):
    fmt.Println("timeout")
}
```
**Ключевые свойства:**  
- Если готово несколько case — выбирается **случайный** (не первый)  
- Если ни один не готов — блокируется до готовности  
- `default` делает `select` неблокирующим
```
select {
case v := <-ch:
    process(v)
default:
    // ничего нет — не блокируемся
}
```
**Типичные применения:**  
- Таймаут на операцию (`time.After`)  
- Отмена через контекст (`ctx.Done()`)  
- Неблокирующий try-receive / try-send  
- Fan-in: слияние нескольких каналов в один
`select` — один из фундаментальных инструментов конкурентности в Go.
25Что такое context и зачем нужен?
Middle
Go
`context.Context` — механизм для **передачи дедлайнов, отмены и метаданных** через цепочку вызовов.
**Зачем нужен:**  
- Отменить длинную операцию (HTTP-запрос отменён клиентом)  
- Установить таймаут на всю цепочку вызовов  
- Передать request-scoped данные (trace ID, user ID)
**Основные функции:**
```
ctx, cancel := context.WithCancel(context.Background())
defer cancel() // всегда вызывать!
ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
ctx = context.WithValue(ctx, keyType{}, value)
```
**Как проверять отмену:**
```
select {
case <-ctx.Done():
    return ctx.Err() // context.Canceled или DeadlineExceeded
default:
}
```
**Правила:**  
- Всегда первым параметром функции: `func Foo(ctx context.Context, ...)`  
- Не хранить в структуре  
- Всегда вызывать `cancel()` через `defer` — иначе утечка горутин  
- `context.Background()` — корень, `context.TODO()` — заглушка когда контекст ещё не определён

28Для чего используется GOMAXPROCS?
Middle
Go
`GOMAXPROCS` задаёт число **логических процессоров (P)**, на которых Go-рантайм может выполнять горутины параллельно.
По умолчанию равен числу CPU-ядер машины (`runtime.NumCPU()`).
```
import "runtime"
runtime.GOMAXPROCS(4) // использовать 4 ядра
n := runtime.GOMAXPROCS(0) // прочитать текущее значение
```
**Что меняет GOMAXPROCS:**  
- При `GOMAXPROCS=1` горутины выполняются конкурентно, но не параллельно — только одна в единицу времени  
- При `GOMAXPROCS=N` до N горутин могут работать реально параллельно на разных ядрах
**Когда менять:**  
- **Уменьшить** — если приложение в контейнере с ограниченным CPU (иначе рантайм «думает», что ядер больше)  
- **Автоматически** через пакет `go.uber.org/automaxprocs` — читает cgroup-лимиты контейнера
```
GOMAXPROCS=2 go run main.go
```
Увеличение сверх числа реальных ядер не даёт прироста — только лишние переключения контекста.
29Что такое планировщик Go и как он работает?
Middle
Go
Планировщик Go — часть рантайма, которая мультиплексирует горутины на системные потоки. Реализует модель **GMP**.
**GMP:**  
- **G (Goroutine)** — горутина со своим стеком и состоянием  
- **M (Machine)** — системный OS-поток  
- **P (Processor)** — логический процессор, очередь горутин + локальное состояние; количество P = GOMAXPROCS
**Как работает:**  
1. Каждый P имеет локальную очередь горутин (runqueue)  
2. M берёт G из очереди своего P и выполняет  
3. Если P пуст — он крадёт горутины у других P (work stealing)  
4. Если G блокируется на syscall — M отсоединяется от P, P берёт другой M (или создаёт новый)
**Точки переключения (preemption):**  
- Вызов функции (stack growth check)  
- Системный вызов / I/O  
- `runtime.Gosched()` — явная уступка  
- С Go 1.14 — асинхронный preemption по сигналу (SIGURG)
Планировщик кооперативно-вытесняющий: горутины не могут занять поток навсегда, но переключение происходит в безопасных точках.

30Как блокирующие системные вызовы влияют на работу планировщика?
Middle
Go
Когда горутина делает **блокирующий syscall** (например, чтение файла, `time.Sleep` в старом коде, `cgo`), рантайм должен не дать системному потоку простаивать.
**Что происходит:**  
1. Горутина G вызывает блокирующий syscall  
2. Рантайм **отсоединяет P от M** — P становится свободным  
3. Свободный P подхватывает другой M (из пула или создаёт новый) и продолжает выполнять другие горутины  
4. Когда syscall завершается — старый M пытается вернуть P; если нет свободного P, G уходит в глобальную очередь
**Почему это важно:**  
Без этого механизма один блокирующий syscall заморозил бы весь P и все горутины в его очереди.
**Сетевой I/O — особый случай:**  
`net` пакет использует **netpoller** (epoll/kqueue) — горутина паркуется без блокировки M. M остаётся свободным для других G. Это почему Go эффективен для сетевых сервисов.
**CGO:** вызовы C кода тоже отсоединяют P — поэтому частые cgo-вызовы дорогие.
31Какие состояния есть у горутины?
Middle
Go
Горутина в Go может находиться в одном из нескольких состояний:
**Основные состояния:**
**Runnable (готова к выполнению)** — горутина стоит в очереди P и ждёт свободного M.
**Running (выполняется)** — горутина активно выполняется на M прямо сейчас.
**Waiting (ожидание)** — горутина заблокирована и не потребляет CPU. Причины:  
- Ожидание канала (`chan send/recv`)  
- `sync.Mutex`, `sync.WaitGroup`  
- `time.Sleep`  
- Сетевой I/O (netpoller)  
- `select`
**Dead (завершена)** — горутина выполнила return или была остановлена паникой. Память стека может быть переиспользована.
**Syscall** — горутина в системном вызове; M отсоединён от P.
**Просмотр состояний:**
```
// При дедлоке Go выводит стек всех горутин с их состоянием
// Вручную:
import "runtime/pprof"
pprof.Lookup("goroutine").WriteTo(os.Stdout, 1)
```
Или через `SIGQUIT` (Ctrl+\) — дамп всех горутин в stderr.
32Как Go поддерживает HTTP/2?
Middle
Go
Go поддерживает HTTP/2 **автоматически** через стандартный пакет `net/http` начиная с Go 1.6.
**Включается автоматически** при использовании TLS:
```
http.ListenAndServeTLS(":443", "cert.pem", "key.pem", handler)
// HTTP/2 активен по умолчанию
```
**Для HTTP без TLS (h2c)** нужен отдельный пакет:
```
import "golang.org/x/net/http2/h2c"
h2s := &http2.Server{}
handler := h2c.NewHandler(myHandler, h2s)
http.ListenAndServe(":8080", handler)
```
**Что даёт HTTP/2:**  
- **Мультиплексирование** — несколько запросов в одном TCP-соединении  
- **Header compression** (HPACK) — меньше трафика  
- **Server Push** — сервер может отправить ресурсы до запроса клиента  
- **Binary protocol** — эффективнее текстового HTTP/1.1
**Управление через `http2.ConfigureServer`:**
```
srv := &http.Server{Addr: ":443", Handler: handler}
http2.ConfigureServer(srv, &http2.Server{
    MaxConcurrentStreams: 250,
})
```
На практике HTTP/2 прозрачен: меняешь `ListenAndServe` на `ListenAndServeTLS` — и всё работает.

}
```
**Заголовок `Location`** — URI созданного ресурса. Клиент может использовать его для последующих запросов (`GET`, `PUT`, `DELETE`). Это часть спецификации HTTP — RFC 9110 рекомендует его для 201-ответов.
**Тело ответа** содержит полную сущность, включая поля, которые сервер сгенерировал сам: `id`, `created_at`, значения по умолчанию, вычисляемые поля. Клиенту не нужно делать дополнительный `GET` после создания — всё уже в ответе.
**Чего избегать:**
**Возвращать только `id`** — клиенту придётся делать лишний `GET`, это дополнительный round-trip и нагрузка.
**Возвращать 200 вместо 201** — семантически неправильно. 200 означает «операция выполнена», 201 явно говорит «ресурс создан».
**Забывать `Location`** — многие REST-клиенты и фронтенд-фреймворки полагаются на этот заголовок для навигации к созданному ресурсу.
34Чем стек отличается от кучи?
Middle
Go
**Стек** — память для локальных переменных и вызовов функций. Выделяется и освобождается автоматически при входе/выходе из функции. Очень быстро — просто сдвиг указателя.
**Куча** — память для данных, которые живут дольше одной функции. Выделяется динамически, освобождается сборщиком мусора (в Go). Медленнее — GC тратит ресурсы на поиск и очистку неиспользуемых объектов.
**В Go** компилятор сам решает, куда поместить переменную — это называется **escape analysis**. Если переменная не «убегает» из функции — стек. Если передаётся наружу (например, возвращается указатель) — куча.
```
func noEscape() int {
    x := 42
    return x // копия значения, x остаётся на стеке
}
func escapes() *int {
    x := 42
    return &x // указатель наружу, x уходит в кучу
}
```
Проверить можно флагом: `go build -gcflags="-m"` — компилятор покажет, какие переменные уходят в кучу.
**Почему это важно:** чем больше аллокаций в куче — тем больше работы у GC, тем выше латентность. В горячих путях стараются держать данные на стеке.
35Как управлять экспортируемостью сущностей в Go?
Middle
Go
В Go нет ключевых слов `public`/`private`. Видимость определяется **регистром первой буквы** имени:
**Заглавная буква** — экспортируемое, доступно из других пакетов: `User`, `GetBalance`, `MaxRetries`.
**Строчная буква** — неэкспортируемое, доступно только внутри своего пакета: `user`, `getBalance`, `maxRetries`.
Это работает для всего: типов, функций, методов, полей структур, констант, переменных.
```
type User struct {
    Name  string // экспортируемое поле — видно снаружи
    email string // неэкспортируемое — только внутри пакета
}
```
**Пакет `internal/`** — дополнительное ограничение на уровне модуля. Код внутри `internal/` доступен только родительскому модулю. Go компилятор это проверяет.
**На практике:** экспортируй минимум — только то, что нужно внешним потребителям. Чем меньше публичный API пакета, тем проще его поддерживать и менять.
36Какие аксиомы каналов знаете?
Middle
Go
**Отправка в nil канал** — блокируется навсегда.
**Чтение из nil канала** — блокируется навсегда.
**Отправка в закрытый канал** — panic.
**Чтение из закрытого канала** — возвращает zero value немедленно (без блокировки). Если канал с буфером то сначала должны считаться все значения из буфера.
**Закрытие nil канала** — panic.
**Повторное закрытие канала** — panic.
**Закрывать канал должен только отправитель** — получатель никогда не закрывает, иначе отправитель получит panic при следующей записи.
**Проверка, закрыт ли канал:** через второе значение при чтении:
```
v, ok := <-ch
// ok == false — канал закрыт и пуст
```
Присваивание `nil` в канал отлючает его кейс в `select`.
37Можно ли через select не только читать, но и писать в каналы?
Middle
Go
Да, `select` работает и на отправку:
```
select {
case ch1 <- value:
    // отправили в ch1
case v := <-ch2:
    // прочитали из ch2
default:
    // никто не готов — идём сюда
}
```
`select` выбирает **первый готовый** case — неважно, чтение это или запись. Если готовы несколько — выбирается случайный.
**Практическое применение** — отправка с таймаутом:
```
select {
case ch <- msg:
    // отправили
case <-time.After(5 * time.Second):
    // получатель не забрал за 5 секунд
}
```
Или неблокирующая отправка — если канал заполнен, не ждём:
```
select {
case ch <- msg:
default:
    // канал полон, пропускаем или логируем
}
```
38Что лежит внутри интерфейса под капотом?
Middle
Go
Интерфейс в Go — это структура из **двух указателей**:
**`type`** — указатель на информацию о конкретном типе (таблица методов, размер, имя типа).
**`data`** — указатель на сами данные.
Когда присваиваешь значение интерфейсу, Go упаковывает его в эту пару:
```
var w io.Writer
w = os.Stdout
// type → *os.File, data → указатель на Stdout
```
**nil интерфейс** — оба поля nil. Но если присвоить типизированный nil, интерфейс **не будет равен nil**:
```
var p *os.File          // p == nil
var w io.Writer = p     // w != nil!
// type → *os.File (не nil), data → nil
```

type error interface {

40Что такое defer?
Middle
Go
`defer` откладывает вызов функции до момента выхода из текущей функции. Выполняется **после return**, но **до возврата значения** вызывающему.
```
func readFile() {
    f, _ := os.Open("file.txt")
    defer f.Close() // закроется при выходе из функции
}
```
Несколько `defer` выполняются в порядке **LIFO** — последний отложенный вызывается первым.
Аргументы `defer` вычисляются **в момент объявления**, а не в момент выполнения:
```
x := 10
defer fmt.Println(x) // напечатает 10, даже если x потом изменится
x = 20
```
41Где используете defer на практике?
Middle
Go
**Закрытие ресурсов** — файлы, соединения к БД, HTTP-тела:
```
resp, _ := http.Get(url)
defer resp.Body.Close()
```
**Освобождение мьютексов:**
```
mu.Lock()
defer mu.Unlock()
```
**Recover от паники:**
```
defer func() {
    if r := recover(); r != nil {
        log.Println("recovered:", r)
    }
}()
```
**Замер времени выполнения:**
```
defer func(start time.Time) {
    log.Printf("took %v", time.Since(start))
}(time.Now())
```
42Почему строки в Go immutable?
Middle
Go
**Безопасность** — строку можно передавать между горутинами без блокировок, потому что никто её не изменит.
**Использование как ключ map** — если бы строку можно было изменить после вставки в map, хэш бы не совпал и данные потерялись.
**Оптимизации компилятора** — можно безопасно переиспользовать одну строку в нескольких местах без копирования.
43Как лучше склеивать много строк?
Middle
Go
**`strings.Builder`** — лучший вариант для склейки в цикле:
```
var b strings.Builder
for _, s := range parts {
    b.WriteString(s)
}
result := b.String()
```
Накапливает байты во внутренний буфер, выделяет память один раз (или несколько при росте). Если размер известен заранее — `b.Grow(n)` убирает лишние аллокации.
**`strings.Join`** — когда уже есть слайс строк:
```
result := strings.Join(parts, ", ")
```
**`fmt.Sprintf`** — для шаблонов с разными типами:
```
result := fmt.Sprintf("user %s, age %d", name, age)
```
**Чего избегать:** конкатенация через `+` в цикле — каждая итерация создаёт новую строку и копирует все предыдущие. На больших объёмах — квадратичная сложность.
44Как держать два слайса независимыми, чтобы изменение в одном не влияло на другой?
Middle
Go
Сделать **явную копию** через `copy`:
```
original := []int{1, 2, 3}
clone := make([]int, len(original))
copy(clone, original)
```
Теперь `clone` имеет **собственный backing array** — изменения в одном слайсе не затронут другой.
**Почему это важно:** простое присваивание `b := a` или `b := a[1:3]` не копирует данные — оба слайса ссылаются на один и тот же массив в памяти. Изменение элемента через один слайс будет видно через другой.
45Можно ли объявить метод с типом ресивера из другого пакета?
Middle
Go
Нет. В Go методы можно объявлять только для типов, определённых **в том же пакете**. Добавить метод к чужому типу напрямую нельзя — компилятор выдаст ошибку.
Обходной путь - создать свой тип на основе чужого:
```
type MyString string
func (s MyString) Shout() string {
    return strings.ToUpper(string(s))
}
```
`MyString` — свой тип в своём пакете, методы можно добавлять свободно.
46Чем отличается defer c функцией и с замыканием?
Middle
Go
**Аргументы** вычисляются **в момент объявления** defer:
```
x := 10
defer fmt.Println(x) // напечатает 10
x = 20
```
**Замыкания** захватывают переменную **по ссылке** и видят её значение **на момент выполнения**:
```
x := 10
defer func() {
    fmt.Println(x) // напечатает 20
}()
x = 20
```
Разница: в первом случае `x` передаётся как аргумент — копируется сразу. Во втором — замыкание ссылается на ту же переменную и читает её при выполнении.
47Что такое OOP? Зачем нужно и как помогает писать код?
Middle
Go
**ООП** — подход, при котором программа строится из объектов, каждый из которых объединяет данные и поведение. Вместо «функция обрабатывает структуру» — «объект сам знает, что с собой делать».
**Инкапсуляция** — объект прячет внутренности и выставляет наружу только то, что нужно. Можно менять реализацию внутри, не ломая код, который этим объектом пользуется.
**Полиморфизм** — разные объекты реагируют на один и тот же вызов по-своему. Вызываешь `Send()` — одна реализация шлёт email, другая — SMS. Вызывающий код не знает и не заботится о конкретном типе.
**Наследование** — переиспользование поведения родителя. В Go классического наследования нет — вместо него **композиция** через встраивание структур, что проще и гибче.
**Зачем нужно:** помогает управлять сложностью. Когда в проекте сотни сущностей, ООП даёт способ разбить систему на независимые части с чёткими границами и контрактами между ними.
48Что будет при panic внутри defer?
Middle
Go
Новая паника **заменяет** предыдущую. Если функция уже паникует и в `defer` происходит ещё одна паника — оригинальная паника теряется, `recover` поймает только последнюю.
```
defer func() {
    recover() // поймает "second", не "first"
}()
defer func() {
    panic("second")
}()
panic("first")
```
Поэтому в `defer` с `recover` важно не допускать паник — иначе можно потерять информацию об исходной ошибке.
49Чем обычный импорт отличается от пустого импорта?
Middle
Go
**Обычный импорт** — подключает пакет для использования в коде. Если импортировал, но не используешь — компилятор выдаст ошибку.
**Пустой импорт** (`_`) — импортирует пакет только ради его побочных эффектов (выполнение `init()` функции). В коде напрямую не используется:
```
import _ "github.com/lib/pq"
```
Здесь `lib/pq` в `init()` регистрирует PostgreSQL-драйвер в `database/sql`. Вызывать из него ничего не нужно, но без импорта драйвер не подключится.
50В чем минус реализации singleton через mutex?
Middle
Go
**Производительность.** Mutex блокирует **каждый вызов** `GetInstance()`, даже когда объект давно создан и все горутины просто хотят его прочитать. Чтение под блокировкой — лишний overhead.
В Go для этого есть `sync.Once` — он гарантирует однократное выполнение и после инициализации **не блокирует** последующие вызовы.
`sync.Once` внутри использует атомарный флаг — после первого вызова проверка практически бесплатна.
51Есть ли разница в порядке полей в struct?
Middle
Go
Да. Из-за **выравнивания памяти** (alignment) компилятор вставляет пустые байты (паддинг) между полями, чтобы каждое поле начиналось с адреса, кратного его размеру.
```
// Неоптимально — 24 байта
type Bad struct {
    a bool   // 1 байт + 7 паддинг
    b int64  // 8 байт
    c bool   // 1 байт + 7 паддинг
}
// Оптимально — 16 байт
type Good struct {
    b int64  // 8 байт
    a bool   // 1 байт
    c bool   // 1 байт + 6 паддинг
}
```
Правило простое: **располагать поля от большего размера к меньшему**. На практике важно для структур, которые создаются миллионами — экономия на каждой складывается в заметный объём памяти.
Проверить можно утилитой `fieldalignment` из `go vet` или пакетом `unsafe.Sizeof()`.

56Как использовать встроенные структуры (embedding)?
Middle
Go
Встраивание это когда мы в структуру добавляем анонимное поле, и методы этого поля становятся доступны на самой структуре.
```
type SafeCounter struct {

}
```
Тут можно звать методы мьютекса на самом SafeCounter и все будет работать.

59Что происходит при попытке изменить символ строки по индексу?
Middle
Go
Если просто попытаемся изменить по индексу то компилятор увидит это как ошибку и не дасть скомпилировать.

```
b := (*byte)(unsafe.Pointer(unsafe.StringData(s)))
*b = 'H' // 💥
```
То тут проблемы.

60Что такое sync.Map, как устроена и когда использовать?
Middle
Go
sync.Map — это две мапы + RWMutex
```
│  read  atomic.Pointer<readOnly> │  ← lock-free чтение
│  dirty map[any]*entry           │  ← защищена Mutex
│  misses int                     │  ← счётчик промахов
```
Чтение:  
1. Ищем в read (атомарно, без лока)  
2. Нашли → возвращаем  
3. Не нашли → локаем mutex, ищем в dirty  
4. После N промахов → dirty повышается до read
Запись:  
1. Если ключ есть в read → атомарно обновляем (без лока!)  
2. Иначе → локаем mutex, пишем в dirty
Хорошо работает когда ключи пишутся один раз, читаются много раз и когда разные горутины работают с разными ключами.
Плохо работает когда есть много записей.

64Задача: найти пересечение двух слайсов
Middle
Ливкодинг
Найти элементы, которые есть в обоих срезах.
**Решение через map — O(n+m):**
```
func intersection(a, b []int) []int {
    set := make(map[int]struct{}, len(a))
    for _, v := range a {
        set[v] = struct{}{}
    }
    var result []int
    for _, v := range b {
        if _, ok := set[v]; ok {
            result = append(result, v)
            delete(set, v) // убираем дубли
        }
    }
    return result
}
// intersection([]int{1,2,3,4}, []int{2,4,5}) → [2, 4]
```
**Если нужны дубли (multiset intersection):**  
Используй `map[int]int` — считай количество вхождений в первом срезе, затем декрементируй при нахождении во втором.
**Сложность:** map-подход — O(n+m) время, O(n) память
65Задача: слить N каналов в один
Middle
Ливкодинг
Классический **fan-in** паттерн — объединить N входных каналов в один выходной.
```
func merge(cs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    forward := func(c <-chan int) {
        defer wg.Done()
        for v := range c {
            out <- v
        }
    }
    wg.Add(len(cs))
    for _, c := range cs {
        go forward(c)
    }
    // Закрываем out когда все источники завершились
    go func() {
        wg.Wait()
        close(out)
    }()
    return out
}
```
**Использование:**
```
ch1 := gen(1, 2, 3)
ch2 := gen(4, 5, 6)
ch3 := gen(7, 8, 9)
for v := range merge(ch1, ch2, ch3) {
    fmt.Println(v) // порядок не гарантирован
}
```
**С поддержкой отмены через context:**
```
forward := func(c <-chan int) {
    defer wg.Done()
    for {
        select {
        case v, ok := <-c:
            if !ok { return }
            out <- v
        case <-ctx.Done():
            return
        }
    }
}
```
Порядок элементов в выходном канале не определён — зависит от скорости горутин.
66Что такое Big O нотация и как она вычисляется?
Middle
Алгоритмы
Big O — метрика роста времени выполнения алгоритма. Также может использоваться как оценка памяти.
Описывает худший кейс.
Например если алгоритм может выполниться за линейное время но в некоторых случаях выполняется за квадратное, то Big O этого алгоритма - квадратное.
O(1) — константа, не зависит от размера  
 пример: получить элемент массива по индексу arr[5]
O(log n) — логарифм, растёт очень медленно  
 пример: бинарный поиск
O(n) — линейный, один проход по данным  
 пример: найти максимум в массиве
O(n log n) — линейно-логарифмический  
 пример: быстрая сортировка (avg)
O(n²) — квадратичный, вложенный цикл  
 пример: сортировка пузырьком
O(2ⁿ) — экспоненциальный, катастрофически быстро растёт

67Что такое коллизии в хеш-таблицах и как с ними бороться?
Middle
Алгоритмы
Коллизия — когда два разных ключа дают одинаковый хеш и попадают в одну ячейку таблицы.
Два способа основных:  
Chaining (цепочки) — каждая ячейка хранит связный список из всех пар ключ значение по этому хешу.
```
[0] → nil
[1] → nil
[2] → nil
[3] → ["alice":25] → ["bob":30] → nil
```
Open Addressing (открытая адресация) — ищем следующую свободную ячейку:
```
hash("alice") = 3 → ячейка 3 свободна → пишем сюда
hash("bob")   = 3 → ячейка 3 занята  → пробуем 4 → свободна → пишем сюда
```
В Go в новой мапе использутся open addressing + linear probing.

69Что такое race condition?
Middle
Многопоточность
Race condition — ситуация, когда результат программы зависит от непредсказуемого порядка выполнения горутин.
Возникает, когда несколько горутин **читают и пишут** одни данные без синхронизации, и итог зависит от того, кто успеет первым.
```
var counter int
go func() { counter++ }()
go func() { counter++ }()
// counter может быть 1 или 2 — не определено
```
**Как обнаружить:** запусти с флагом `-race`:
```
go test -race ./...
go run -race main.go
```
**Как исправить:** использовать `sync.Mutex`, `sync/atomic` или каналы для координации доступа.
Race condition — логическая проблема: даже если каждая операция атомарна, их комбинация может дать неверный результат.
70Что такое data race?
Middle
Многопоточность
Data race — конкретный вид race condition: **две горутины одновременно обращаются к одной переменной, хотя бы одна пишет, и нет синхронизации**.
Go детектирует data race инструментом `-race` (использует ThreadSanitizer). Он добавляет shadow memory к каждой переменной и отслеживает доступы.
```
var x int
go func() { x = 1 }()  // write
go func() { _ = x }()  // read — data race!
```
**Отличие от race condition:**  
- Data race — строго про **одновременный доступ к памяти** без синхронизации  
- Race condition — шире: логическая ошибка из-за порядка выполнения; может быть даже без data race
**Решение:**
```
var mu sync.Mutex
mu.Lock(); x = 1; mu.Unlock()
```
Data race — undefined behaviour в Go: компилятор не гарантирует никакого конкретного результата.
71Когда следует использовать sync.RWMutex?
Middle
Многопоточность
`sync.RWMutex` нужен, когда чтений **значительно больше**, чем записей, и чтения безопасно выполнять параллельно.
**Отличие от `sync.Mutex`:**  
- `Mutex` — один лок для всех: и для чтения, и для записи  
- `RWMutex` — позволяет **множество одновременных читателей**, но запись эксклюзивна
```
var mu sync.RWMutex
var cache map[string]string
// Чтение — параллельно
mu.RLock()
val := cache[key]
mu.RUnlock()
// Запись — эксклюзивно
mu.Lock()
cache[key] = val
mu.Unlock()
```
**Когда НЕ стоит использовать:**  
- Когда записей столько же, сколько чтений — `RWMutex` тяжелее обычного `Mutex`  
- Для защиты очень коротких операций — оверхед на управление локом может перевесить выгоду
**Правило:** если профилирование показывает contention на `Mutex` при преобладании чтений — переходи на `RWMutex`.
72Что такое sync.Cond и зачем нужно?
Middle
Многопоточность
`sync.Cond` — примитив синхронизации для ожидания наступления условия с возможностью эффективно будить горутины.
**Зачем нужен:** когда горутина должна ждать, пока что-то **изменится**, и не хочется делать busy-wait (цикл с `time.Sleep`).
```
var mu sync.Mutex
cond := sync.NewCond(&mu)
ready := false
// Ожидающая горутина
go func() {
    mu.Lock()
    for !ready {
        cond.Wait() // освобождает mu и ждёт сигнала
    }
    mu.Unlock()
}()
// Сигнализирующая горутина
mu.Lock()
ready = true
cond.Signal() // или Broadcast() для всех
mu.Unlock()
```
**Методы:**  
- `Wait()` — атомарно освобождает mutex и засыпает  
- `Signal()` — будит одну горутину  
- `Broadcast()` — будит все ожидающие горутины
**Важно:** `Wait()` всегда вызывать в цикле `for !condition` — spurious wakeup возможен.
На практике `sync.Cond` редко нужен: чаще достаточно каналов или `sync.WaitGroup`.
73В чем отличие горутины от системного потока?
Middle
Многопоточность
Горутина — **легковесный поток выполнения**, управляемый Go-рантаймом, а не ОС.
**Системный поток (OS thread):**  
- Создаётся ОС, стек ~1–8 МБ фиксированный  
- Переключение контекста — дорогое (syscall)  
- Типично сотни–тысячи потоков на процесс
**Горутина:**  
- Создаётся рантаймом Go, начальный стек ~2–8 КБ, растёт динамически  
- Переключение — дешёвое, в userspace  
- Миллионы горутин — нормальная практика
74Что такое deadlock и как его избежать?
Middle
Многопоточность
Deadlock — ситуация, когда две или более горутины **бесконечно ждут друг друга**, и ни одна не может продолжить выполнение.
```
var mu1, mu2 sync.Mutex
go func() {
    mu1.Lock(); mu2.Lock() // ждёт mu2
    // ...
}()
go func() {
    mu2.Lock(); mu1.Lock() // ждёт mu1 — deadlock
    // ...
}()
```
Go рантайм **обнаруживает** полный deadlock (все горутины заблокированы) и паникует:
**Как избежать:**  
- Всегда захватывать мьютексы в **одном и том же порядке**  
- Использовать `defer mu.Unlock()` сразу после `Lock()`  
- Предпочитать каналы мьютексам там, где это естественно  
- Устанавливать таймауты через `context` или `select` с `default`
```
mu.Lock()
defer mu.Unlock()
```
Частая причина — удержание лока при вызове внешней функции, которая тоже пытается его захватить.
75Почему канал должен закрывать sender, а не receiver?
Middle
Многопоточность
Правило Go: **только тот, кто пишет в канал (sender), должен его закрывать**. Receiver закрывать не должен.
**Почему:**  
Если sender отправит в уже закрытый канал — будет **паника**:
```
ch := make(chan int)
close(ch)
ch <- 1 // panic: send on closed channel
```
Receiver не знает, когда sender закончил — он не может безопасно закрыть канал.
**Правильный паттерн:**
```
func producer(ch chan<- int) {
    defer close(ch) // sender закрывает
    for i := 0; i < 5; i++ {
        ch <- i
    }
}
func consumer(ch <-chan int) {
    for v := range ch { // range завершится при close
        fmt.Println(v)
    }
}
```
**Несколько senderов:** когда горутин-отправителей несколько, используют `sync.WaitGroup` + отдельную горутину-координатор, которая закрывает канал после завершения всех senderов.
Закрытый канал можно читать: он вернёт оставшиеся значения, затем zero value и `false` при двухзначном получении.
76Чем опасен race condition на map и как его решать?
Middle
Многопоточность
Встроенный `map` в Go **не потокобезопасен**: параллельные чтение+запись или две записи вызовут панику с сообщением `concurrent map read and map write`.
**Почему опасен:**  
Go рантайм детектирует конкурентный доступ к map и **падает** — это намеренное поведение, не UB.
**Решение 1 — `sync.Mutex`:**
```
var mu sync.Mutex
var m = make(map[string]int)
mu.Lock()
m[key] = val
mu.Unlock()
```
**Решение 2 — `sync.RWMutex`** (если чтений больше, чем записей):
```
mu.RLock(); v := m[key]; mu.RUnlock()
```
**Решение 3 — `sync.Map`** (из стандартной библиотеки):
```
var m sync.Map
m.Store(key, val)
v, ok := m.Load(key)
```
`sync.Map` оптимален для паттерна «много чтений, редкие записи» или когда ключи не пересекаются между горутинами. Для общего случая — проще и понятнее `map` + `sync.Mutex`.
77Чем отличается sync/atomic от mutex? Когда что использовать?
Middle
Многопоточность
**`sync/atomic`** — низкоуровневые атомарные операции над примитивными типами (int32, int64, pointer и др.).  
**`sync.Mutex`** — высокоуровневый лок для защиты произвольных блоков кода.
**Когда atomic:**  
- Одна переменная (счётчик, флаг)  
- Операции: инкремент, CAS (compare-and-swap), load/store  
- Максимальная производительность, нет блокировки потока
```
var counter int64
atomic.AddInt64(&counter, 1)   // безопасно из любой горутины
atomic.LoadInt64(&counter)
```
**Когда Mutex:**  
- Несколько переменных нужно изменить **атомарно вместе**  
- Сложная логика внутри критической секции  
- Структуры, слайсы, map
```
mu.Lock()
balance -= amount
log = append(log, amount) // два поля вместе
mu.Unlock()
```
**Итог:** atomic — для простых счётчиков и флагов. Mutex — для всего остального. Не пытайся реализовать сложную синхронизацию через atomic: это путь к тонким багам.
78Что такое false sharing и как он влияет на производительность?
Middle
Многопоточность
False sharing — когда **два независимых поля** попадают в одну кэш-линию CPU (обычно 64 байта), и запись в одно из них инвалидирует кэш другого у соседнего ядра.
**Проблема:** CPU синхронизирует кэш на уровне кэш-линий, а не байтов. Два ядра «дерутся» за одну линию, хотя работают с разными данными.
```
// Плохо: counter1 и counter2 в одной кэш-линии
type Counters struct {
    c1 int64
    c2 int64
}
// Хорошо: padding разносит по разным кэш-линиям
type Counter struct {
    val int64
    _   [56]byte // pad до 64 байт
}
```
Что тут происходит  
int64 занимает 8 байт.  
Остальные 56 байт нужны, чтобы общий размер структуры стал:  
8 + 56 = 64 байта  
А 64 байта — это типичный размер cache line на современных CPU.
**Когда актуально:**  
- Горячие счётчики, обновляемые разными горутинами параллельно  
- Высоконагруженные структуры с параллельным доступом к разным полям
**Как обнаружить:** `perf stat` (Linux) или профилирование с hardware counters — ищи `cache-misses`.
На практике false sharing редко оптимизируют заранее — только если профилирование показывает конкретную проблему.
79Чем опасен sync.Pool, особенно для больших объектов?
Middle
Многопоточность
`sync.Pool` — пул для **переиспользования временных объектов**, чтобы снизить давление на GC.
```
var pool = sync.Pool{
    New: func() any { return make([]byte, 4096) },
}
buf := pool.Get().([]byte)
defer pool.Put(buf)
```
**Чем опасен для больших объектов:**
**1. GC может очистить пул в любой момент** — между двумя циклами GC объекты исчезают. Нельзя рассчитывать на долгое хранение.
**2. Большие объекты в пуле дольше живут** — GC видит их как живые, пока они в пуле. Это может **увеличить** давление на память, а не снизить.
**3. Объект возвращается «грязным»** — нужно сбрасывать состояние перед Put или после Get:
```
buf = buf[:0] // сброс длины среза перед возвратом в пул
pool.Put(buf)
```
**4. Нет гарантии, что получишь тот же объект** — Pool не стек, не очередь.
**Когда подходит:** мелкие короткоживущие объекты — буферы, `bytes.Buffer`, парсеры. Для больших объектов с нефиксированным размером — лучше просто аллоцировать.
80Почему именно возникает блокировка при работе с nil-каналом?
Middle
Многопоточность
Nil-канал **навсегда блокирует** любую операцию отправки или получения — горутина засыпает и никогда не просыпается.
```
var ch chan int // nil
ch <- 1   // блокируется навсегда
<-ch      // блокируется навсегда
```
**Почему так:** канал — это указатель на внутреннюю структуру. У nil нет очереди и нет механизма пробуждения — рантайму некуда поставить горутину в очередь ожидания.
**В select nil-канал игнорируется** — это полезное свойство:
```
var optional chan int // nil
select {
case v := <-optional: // этот case никогда не выбирается
    use(v)
case v := <-active:
    use(v)
}
```
**Паттерн отключения case в select:** установи канал в `nil`, чтобы динамически исключить его из `select` после закрытия:
```
if ch1 == nil && ch2 == nil {
    return // оба закрыты
}
```
Закрытый канал — не nil: из него можно читать (возвращает zero value). Nil и закрытый — разные состояния.
81Что можно использовать для передачи данных между горутинами?
Middle
Многопоточность
Для передачи данных между горутинами в Go есть два основных инструмента: **каналы** и **разделяемая память с синхронизацией**.
**Каналы — идиоматичный способ:**
```
ch := make(chan int, 1)
go func() { ch <- 42 }()
v := <-ch
```
Подходят для передачи данных и сигналов. Следуют принципу Go: «не общайся через разделяемую память — разделяй память через общение».
**Разделяемая память + sync.Mutex:**
```
var mu sync.Mutex
var shared map[string]int
mu.Lock()
shared["key"] = 1
mu.Unlock()
```
Подходит, когда нужен общий кэш или состояние.
**sync/atomic** — для примитивов (счётчики, флаги):
```
var counter int64
atomic.AddInt64(&counter, 1)
```
**sync.Map** — потокобезопасная map без явного мьютекса.
**Выбор:** каналы — для передачи ownership и событий; mutex — для разделяемого состояния; atomic — для одиночных переменных.
82Какие типы каналов есть и для чего используются?
Middle
Многопоточность
В Go три типа каналов по направленности и два по буферизации.
**По направленности:**
```
chan int      // двунаправленный
chan<- int    // только запись (send-only)
<-chan int    // только чтение (receive-only)
```
Направленные каналы используют в сигнатурах функций для явного указания роли:
```
func producer(out chan<- int) { out <- 1 }
func consumer(in <-chan int)  { v := <-in }
```
**По буферизации:**
**Небуферизованный** (`make(chan T)`) — синхронный: отправитель блокируется до тех пор, пока получатель не прочитает.
**Буферизованный** (`make(chan T, n)`) — асинхронный до заполнения буфера: отправитель блокируется только когда буфер полон.
```
ch := make(chan int, 3)
ch <- 1 // не блокируется
ch <- 2 // не блокируется
ch <- 3 // не блокируется
ch <- 4 // блокируется — буфер полон
```
**Когда что использовать:**  
- Небуферизованный — синхронизация, рандеву между горутинами  
- Буферизованный — сглаживание пиков, pipeline с разной скоростью producer/consumer
83Что знаешь из пакета sync?
Middle
Многопоточность
Пакет `sync` содержит примитивы синхронизации для работы с разделяемым состоянием.
**Основные типы:**
**`sync.Mutex`** — взаимное исключение. `Lock()` / `Unlock()`.
**`sync.RWMutex`** — читатели параллельны, запись эксклюзивна. `RLock()` / `RUnlock()` / `Lock()` / `Unlock()`.
**`sync.WaitGroup`** — ожидание завершения группы горутин. `Add()` / `Done()` / `Wait()`.
**`sync.Once`** — выполнить функцию ровно один раз (синглтон, ленивая инициализация):
```
var once sync.Once
once.Do(func() { /* инициализация */ })
```
**`sync.Cond`** — ожидание условия с пробуждением через `Signal()` / `Broadcast()`.
**`sync.Map`** — потокобезопасная map: `Store()`, `Load()`, `Delete()`, `Range()`.
**`sync.Pool`** — пул переиспользуемых объектов для снижения давления на GC.
**Правило выбора:** если передаёшь данные — канал; если защищаешь разделяемое состояние — `sync.Mutex`; если ждёшь горутины — `WaitGroup`.
84Расскажи подробнее про WaitGroup: для чего нужен и какие у него методы?
Middle
Многопоточность
`sync.WaitGroup` — примитив для ожидания завершения группы горутин.
**Четыре метода:**
**`Add(n int)`** — увеличивает счётчик на n (вызывай до запуска горутины).
**`Done()`** — уменьшает счётчик на 1 (эквивалент `Add(-1)`).
**`Wait()`** — блокируется, пока счётчик не станет равен 0.
**`Go(f func())`** — добавлен в **Go 1.25**. Оборачивает `Add(1)` + запуск горутины + `defer Done()` в один вызов. Внутри реализован так:
```
func (wg *WaitGroup) Go(f func()) {
    wg.Add(1)
    go func() {
        defer wg.Done()
        f()
    }()
}
```
**Пример до Go 1.25:**
```
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        process(id)
    }(i)
}
wg.Wait()
```
**Пример с Go 1.25+:**
```
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Go(func() {
        process(i)
    })
}
wg.Wait()
```
Обрати внимание: `wg.Go()` сам запускает горутину — **не нужно писать `go`** перед ним. Также **не нужно вызывать `Done()`** — метод делает это автоматически.
**Частые ошибки:**
**`Add()` внутри горутины** — гонка: `Wait()` может сработать раньше. В Go 1.25+ `go vet` ловит эту ошибку.
**Забыть `Done()`** — `Wait()` зависнет навсегда. Решается переходом на `wg.Go()`.
**Передавать `WaitGroup` по значению** — всегда передавай указатель или через замыкание.
**Когда не хватает WaitGroup:** если нужно ещё и собирать ошибки или отменять горутины — используй `errgroup` из `golang.org/x/sync/errgroup`, который предоставляет `g.Go()` с возвратом ошибки и отменой через `context`.
85Какие паттерны конкурентности знаешь?
Middle
Многопоточность
Основные паттерны конкурентности в Go:
**Pipeline** — цепочка горутин, каждая обрабатывает данные и передаёт дальше через каналы:
```
gen -> square -> print
```
**Fan-out** — один канал читают несколько горутин параллельно (распределение работы).
**Fan-in** — несколько каналов сливаются в один (агрегация результатов).
**Worker Pool** — фиксированное число горутин разбирают задачи из очереди:
```
jobs := make(chan Job, 100)
for i := 0; i < numWorkers; i++ {
    go worker(jobs)
}
```
**Done channel / Context cancellation** — сигнал остановки через `ctx.Done()` или закрытие канала.
**Semaphore** — ограничение числа параллельных операций через буферизованный канал:
```
sem := make(chan struct{}, maxConcurrent)
sem <- struct{}{}
defer func() { <-sem }()
```
**Or-done** — обёртка над `select` для прекращения чтения при отмене контекста.
**Timeout** — `select` с `time.After` или `context.WithTimeout`.
86Расскажи про fan-in. Для чего он нужен?
Middle
Многопоточность
**Fan-in** — паттерн слияния нескольких входных каналов в один выходной.
**Зачем нужен:** когда несколько горутин-производителей генерируют данные параллельно, а потребитель должен читать из одного канала.
```
func fanIn(cs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, c := range cs {
        wg.Add(1)
        go func(ch <-chan int) {
            defer wg.Done()
            for v := range ch {
                out <- v
            }
        }(c)
    }
    go func() {
        wg.Wait()
        close(out) // закрываем когда все источники иссякли
    }()
    return out
}
```
**Использование:**
```
ch1, ch2, ch3 := producer1(), producer2(), producer3()
for v := range fanIn(ch1, ch2, ch3) {
    process(v)
}
```
**Типичное применение:** параллельные HTTP-запросы, параллельная обработка файлов, агрегация результатов воркеров.
Обратный паттерн — **fan-out**: один канал читают несколько горутин.
87Расскажи про паттерн semaphore.
Middle
Многопоточность
**Semaphore** — паттерн ограничения числа одновременно выполняемых операций.
В Go реализуется через **буферизованный канал**: размер буфера = максимальное число параллельных операций.
```
sem := make(chan struct{}, 5) // не более 5 параллельно
for _, url := range urls {
    sem <- struct{}{}         // захватываем слот (блокируется при заполнении)
    go func(u string) {
        defer func() { <-sem }() // освобождаем слот
        fetch(u)
    }(url)
}
// Ждём завершения всех
for i := 0; i < cap(sem); i++ {
    sem <- struct{}{}
}
```
**Зачем нужен:**  
- Ограничить нагрузку на внешний API (rate limiting)  
- Контролировать число открытых файлов / соединений  
- Не перегрузить CPU пулом горутин
**Альтернатива:** пакет `golang.org/x/sync/semaphore` — взвешенный семафор с поддержкой контекста:
```
sem := semaphore.NewWeighted(5)
sem.Acquire(ctx, 1)
defer sem.Release(1)
```
Worker pool — похожий паттерн, но семафор проще когда задачи разнородны.
88Что происходит с горутиной при блокировке на mutex?
Middle
Многопоточность
Горутина **уходит в ожидание** и не занимает процессорное время. Go-рантайм снимает её с потока ОС и ставит в очередь ожидания мьютекса. Поток освобождается и выполняет другие горутины.
Внутри мьютекса есть **очередь ожидания** (wait queue) — связный список заблокированных горутин. Когда горутина вызывает `Lock()` на занятом мьютексе, рантайм добавляет её в эту очередь и переводит в статус **waiting**.
**Будит** горутину тот, кто вызвал `Unlock()`. При разблокировке рантайм достаёт первую горутину из очереди и переводит её в статус **runnable** — после этого планировщик Go подхватит её и поставит на выполнение на свободный поток.
89Как работает LEFT JOIN?
Middle
SQL
LEFT JOIN возвращает все строки из левой таблицы и совпадающие строки из правой; если совпадения нет — поля правой таблицы будут NULL.
Порядок важен: «левая» таблица — та, что в FROM, «правая» — та, что после LEFT JOIN.
Типичный сценарий — получить всех пользователей даже если у них нет заказов:
```
SELECT u.*, o.id FROM users u 
LEFT JOIN orders o 
ON o.user_id = u.id.
```
90В чем плюсы и минусы индексов на всех полях?
Middle
SQL
Плюс индекса — ускорение SELECT с фильтрацией, сортировкой и JOIN.
Минусы - при INSERT, UPDATE, DELETE все индексы перестраиваются, что замедляет запись. Если проиндексировать все поля, overhead на write-операции может стать критичным при высокой частоте вставок.
Также планировщик может выбрать неоптимальный индекс при их избытке, получив хуже, чем Seq Scan.
Индексы тратят место на диске.
Хорошая практика — индексировать только поля, реально участвующие в WHERE, JOIN ON или ORDER BY, и проверять статистику через pg\_stat\_user\_indexes.
91В чем разница между синхронной и асинхронной репликацией?
Middle
SQL
При синхронной репликации мастер считает транзакцию подтверждённой только после того, как реплика записала изменения — это гарантирует что данные не пропадут, но увеличивает время каждого коммита.
При асинхронной репликации мастер подтверждает транзакцию немедленно, не дожидаясь реплики — запись быстрее, но при падении мастера часть последних транзакций может быть потеряна.
В PostgreSQL синхронная репликация включается параметром synchronous\_commit = on и указанием synchronous\_standby\_names.
Асинхронные реплики чтения — стандартная практика для масштабирования SELECT-нагрузки. Типичная продакшн-схема: один синхронный standby для надёжности и несколько асинхронных для балансировки чтения.
92Как решал проблемы производительности запросов к БД?
Middle
SQL
Первый шаг — **EXPLAIN (ANALYZE, BUFFERS)** для понимания плана: какие узлы дорогие, есть ли Seq Scan на большой таблице, точны ли оценки планировщика. Затем смотрю на наличие нужных индексов — часто причиной является отсутствие индекса на внешнем ключе или поле в `WHERE`.
Ещё частая проблема — **функции над индексированной колонкой** в `WHERE` (например, `DATE(created_at) = today` вместо диапазона), что ломает использование индекса.
Если запрос исторически медленный по природе — рассматриваю **материализованные представления** или **кеш в Redis**. Для аналитики тяжелее — выносим в OLAP или агрегируем заранее.
93Приведи пример индекса, который ты настраивал в PostgreSQL.
Middle
SQL
Один из примеров — **частичный индекс** на таблице заказов:
```
CREATE INDEX idx_orders_pending ON orders(created_at) WHERE status = 'pending';
```
Полный индекс по `created_at` покрывал все 10 млн строк, тогда как активных заказов ~50 тыс — частичный индекс **в 200 раз меньше** и работает быстрее.
Другой пример — **составной индекс**:
```
CREATE INDEX idx_events_user_time ON events(user_id, created_at DESC);
```
Он оптимизирует запросы «последние события пользователя»: `user_id` идёт первым (условие равенства), `created_at` вторым с `DESC` — план сразу возвращает отсортированные данные **без дополнительной сортировки**.
В обоих случаях решение принималось после **EXPLAIN ANALYZE**, который показал Seq Scan с большим числом строк.
94Какие поля следует индексировать?
Middle
SQL
Индексировать стоит поля, которые часто встречаются в `WHERE`, `JOIN ON`, `ORDER BY` и `GROUP BY`.
В первую очередь — **внешние ключи**: без индекса `JOIN` даёт Seq Scan по всей таблице.
**Хорошие кандидаты**: поля с высокой селективностью (много уникальных значений), поля для диапазонных запросов (даты, числа), поля статуса где «активных» записей немного (тогда выгоден **частичный индекс**).
**Не стоит индексировать**: булевые поля с равномерным распределением, поля которые не участвуют в фильтрации, маленькие таблицы (Seq Scan на 1000 строк быстрее).
Неиспользуемые индексы видны через `pg_stat_user_indexes` — их стоит удалять, чтобы не замедлять запись.
95Какой индекс стоит сделать для дат?
Middle
SQL
Для дат по умолчанию подходит **B-tree индекс** — PostgreSQL оптимизирует `<`, `>`, `BETWEEN`, `ORDER BY`.
**Главное правило**: не применять функции над индексированной колонкой в `WHERE`, иначе индекс не используется. Вместо `DATE(created_at) = '2024-01-01'` пишем:
```
created_at >= '2024-01-01' AND created_at < '2024-01-02'
```
Если запросы всегда берут «свежие» данные (последние 30 дней из таблицы за 5 лет), выгоден **частичный индекс**:
```
CREATE INDEX idx_events_recent ON events(created_at)
WHERE created_at > NOW() - INTERVAL '30 days';
```
Для append-only таблиц с хронологическими данными (логи) стоит рассмотреть **BRIN-индекс** — он в 100–1000 раз меньше B-tree и эффективен, когда строки физически хранятся в порядке возрастания даты.
96Какой должен быть порядок полей в составном индексе?
Middle
SQL
**Основное правило**: поля с условием равенства (`=`) — на первые позиции, поля с диапазоном (`<`, `>`, `BETWEEN`, `LIKE prefix`) — последними. B-tree обходится слева направо, и при первом диапазонном условии следующие поля уже не помогают фильтрации.
Пример: для `WHERE user_id = $1 AND created_at > $2` правильный индекс — `(user_id, created_at)`, а не наоборот.
Если несколько полей равенства — вперёд ставим поле с **наибольшей селективностью**.
Для **покрывающего индекса** (index-only scan) добавляем `SELECT`-поля через `INCLUDE`:
```
CREATE INDEX idx ON orders(user_id, created_at) INCLUDE (status, total);
```
Это позволяет отдавать данные **без обращения к heap**.
97Как посмотреть, использовался индекс или нет?
Middle
SQL
Основной инструмент — **EXPLAIN (ANALYZE, BUFFERS)**:
```
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```
В плане видно **Index Scan / Index Only Scan** — индекс используется, **Seq Scan** — нет. `BUFFERS` показывает количество обращений к диску и shared hit (кеш).
**Важно**: `EXPLAIN` без `ANALYZE` — только оценочный план планировщика, с `ANALYZE` — реальное выполнение с замерами времени и числа строк.
Для просмотра статистики использования индексов есть системное представление:
```
SELECT indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE relname = 'your_table';
```
Если `idx_scan = 0` — индекс не использовался с момента последнего сброса статистики.
Также полезна **pg\_stat\_statements** для поиска самых тяжёлых запросов в целом по системе.
98Что такое Seq Scan и что он означает?
Middle
SQL
**Seq Scan** (Sequential Scan) — полное последовательное чтение таблицы строка за строкой без использования индекса.
Планировщик выбирает его когда: нет подходящего индекса, выборка затрагивает большую долю строк (обычно >10–20% таблицы), или таблица маленькая и индекс добавляет лишний overhead.
Сам по себе Seq Scan — **не всегда проблема**: на таблице в 1000 строк он быстрее Index Scan. **Проблема** — Seq Scan на таблице в миллионы строк с небольшой выборкой: это сигнал добавить индекс.
В `EXPLAIN` сравнивают «оценочное rows» и реальное количество строк — большое расхождение означает **устаревшую статистику** таблицы, тогда помогает `ANALYZE` или уменьшение autovacuum-порогов.
99Чем отличается EXPLAIN от EXPLAIN ANALYZE?
Middle
SQL
EXPLAIN показывает план выполнения запроса, который планировщик построил на основе статистики — без реального выполнения. Все числа (cost, rows) — оценки.
EXPLAIN ANALYZE реально выполняет запрос и добавляет фактические данные: сколько строк обработано и сколько времени потратил каждый узел плана.
```
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- Seq Scan on orders  (cost=0.00..184.00 rows=12 width=64)
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42;
-- Seq Scan on orders  (cost=0.00..184.00 rows=12 width=64)
--                     (actual time=0.08..2.31 rows=9 loops=1)
-- Buffers: shared hit=84
```
Ключевые поля с ANALYZE: `actual time` — реальное время узла, `actual rows` — реальное число строк. Большое расхождение между `rows` (оценка) и `actual rows` — признак устаревшей статистики, нужен `ANALYZE` на таблице.
`BUFFERS` показывает `shared hit` (прочитано из кеша) и `shared read` (прочитано с диска). Для диагностики всегда используй `EXPLAIN (ANALYZE, BUFFERS)`.
100Какой самый сложный запрос тебе приходилось разбирать через EXPLAIN ANALYZE?
Middle
SQL
Запрос с тремя `JOIN` на таблице событий (~50M строк), который выполнялся **8 секунд**:
```
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.id, u.name, COUNT(e.id) AS cnt
FROM users u
JOIN events e ON e.user_id = u.id
JOIN sessions s ON s.user_id = u.id
WHERE e.created_at > NOW() - INTERVAL '30 days'
  AND s.expires_at > NOW()
GROUP BY u.id, u.name
HAVING COUNT(e.id) > 100;
```
`EXPLAIN ANALYZE` показал **Hash Join** с `Batches: 8` — hash-таблица не влезала в `work_mem` и шла на диск. Также был **Seq Scan по events** с `actual rows=2 000 000` при оценке планировщика `rows=50 000` — сильное расхождение из-за коррелированных условий по дате, статистика не отражала реальный перекос данных.
**Решение**: добавили составной индекс `(user_id, created_at)`, переписали `WHERE` чтобы индекс использовался, подняли `work_mem` для тяжёлых аналитических запросов до **64MB**. Время выполнения упало до **0.3 секунды**.

101Как вы работаете с транзакциями в Go коде?
Middle
SQL
Открываем транзакцию через `db.BeginTx`, все операции выполняем через `tx`, в defer делаем rollback при ошибке и commit при успехе.
```
func (s *Service) Transfer(ctx context.Context, from, to int, amount int64) (err error) {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer func() {
        if err != nil {
            tx.Rollback()
        } else {
            err = tx.Commit()
        }
    }()
    _, err = tx.ExecContext(ctx,
        `UPDATE accounts SET balance = balance - $1 WHERE id = $2`,
        amount, from)
    if err != nil {
        return err
    }
    _, err = tx.ExecContext(ctx,
        `UPDATE accounts SET balance = balance + $1 WHERE id = $2`,
        amount, to)
    return err
}
```
Использую `BeginTx` с контекстом — это позволяет прервать транзакцию при таймауте. Переменная `err` именованная в возвращаемых значениях — defer видит её и принимает решение: rollback или commit. Все операции внутри транзакции выполняются через `tx`, не через `db`.
102Где в сервисе открывается транзакция, если есть несколько запросов к базе?
Middle
SQL
Транзакция открывается на уровне сервисного слоя (usecase/service), не в репозитории и не в хендлере. Репозиторий принимает интерфейс `DBTX`, который реализуют и `*sql.DB`, и `*sql.Tx`.
```
// Интерфейс — общий для db и tx
type DBTX interface {
    ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
    QueryRowContext(ctx context.Context, query string, args ...any) *sql.Row
    QueryContext(ctx context.Context, query string, args ...any) (*sql.Rows, error)
}
type UserRepo struct{ db DBTX }
// В сервисе:
func (s *Service) CreateOrderWithItems(ctx context.Context, order Order, items []Item) (err error) {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer func() {
        if err != nil {
            tx.Rollback()
        } else {
            err = tx.Commit()
        }
    }()
    repo := &UserRepo{db: tx} // репозиторий работает через транзакцию
    orderID, err := repo.CreateOrder(ctx, order)
    if err != nil {
        return err
    }
    return repo.CreateItems(ctx, orderID, items)
}
```
Репозитории при этом не знают о транзакции — они просто используют переданный DBTX.
103Какую библиотеку/пакет вы используете для работы с Postgres?
Middle
SQL
Стандарт для большинства Go-проектов — `pgx` + `pgxpool`:
```
import "github.com/jackc/pgx/v5/pgxpool"
pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
if err != nil {
    log.Fatal(err)
}
defer pool.Close()
var name string
err = pool.QueryRow(ctx,

```
`pgx` быстрее устаревшего `lib/pq`, поддерживает нативные типы PostgreSQL (массивы, JSONB, UUID без конвертации в строку), именованные параметры, pipeline-запросы. `pgxpool` — встроенный пул соединений.
Поверх pgx часто используют:  
- `sqlc` — генерация типобезопасного Go-кода из SQL-файлов, нет runtime overhead.  
- `sqlx` — удобный scan в структуры через теги, совместим со стандартным `database/sql`.
104Какие настройки ты бы задал сам при конфигурации клиента для подключения к базе?
Middle
SQL
```
config, _ := pgxpool.ParseConfig(dsn)
config.MaxConns = 20                        // максимум соединений в пуле
config.MinConns = 2                         // держать минимум открытых
config.MaxConnLifetime = 30 * time.Minute   // переоткрывать соединение раз в 30 мин
config.MaxConnIdleTime = 5 * time.Minute    // закрывать простаивающее через 5 мин
config.HealthCheckPeriod = 1 * time.Minute  // пинговать соединения в пуле
pool, _ := pgxpool.NewWithConfig(ctx, config)
```
Таймауты на каждый запрос — через контекст, не через глобальные настройки:
```
ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()
row := pool.QueryRow(ctx, `SELECT ...`)
```
`MaxConnLifetime` важен чтобы переоткрывать соединения после failover реплики или балансировщика. `MaxConnIdleTime` — чтобы не держать лишние соединения при низкой нагрузке. Таймаут через контекст позволяет отменить зависший запрос, не ломая пул.
105Чем ситуация с одним соединением отличается от ситуации с пулом соединений?
Middle
SQL
Одно соединение — все запросы выполняются последовательно. Если два хендлера одновременно обращаются к БД, один ждёт пока другой закончит. При большой нагрузке это замедляет приложение.
С пулом параллельные запросы берут свободное соединение и выполняются одновременно. Производительность системы кратно выше.
Дополнительный плюс пула — соединения переиспользуются. Установка нового TCP-соединения к PostgreSQL стоит 10–50мс (handshake + аутентификация). Пул держит соединения открытыми и раздаёт их снова, избегая этих затрат на каждый запрос.
Без пула Go-сервис с тысячами горутин фактически упирается в одно соединение, независимо от количества CPU.
106Какие проблемы решает пул соединений?
Middle
SQL
Пул соединений решает несколько проблем одновременно:
1. Параллелизм — несколько запросов к БД выполняются одновременно, не блокируют друг друга.
2. Стоимость подключения — TCP handshake + TLS + аутентификация PostgreSQL занимают 10–50мс. Пул держит соединения открытыми и переиспользует их.
3. Лимит на стороне Postgres — `max_connections` обычно 100–300. Пул контролирует, сколько соединений открыто от сервиса, не давая превысить лимит.
4. Ожидание вместо ошибки — если все соединения заняты, новый запрос встаёт в очередь и ждёт до таймаута, а не получает ошибку сразу.
5. Health check — пул пингует соединения и переоткрывает упавшие. Сервис не отдаёт ошибки на мёртвых соединениях после перезапуска БД или failover.
107Что делать, если у одного инстанса пул на 10 соединений, а инстансов 10, и Postgres не выдерживает 100 соединений?
Middle
SQL
Решение — поставить connection pooler между сервисами и Postgres. Стандарт в мире PostgreSQL — PgBouncer.
```
[svc1,  пул 10] ─┐
[svc2,  пул 10] ─┤                          ┌── PostgreSQL
...              ─┼── PgBouncer (10–20 conn) ─┤   max_connections=100
[svc10, пул 10] ─┘                          └── (остаток для replication, superuser)
```
PgBouncer принимает до N «виртуальных» соединений от клиентов, а к Postgres держит гораздо меньше реальных. В режиме `transaction pooling` одно реальное соединение обслуживает десятки клиентских — соединение возвращается в пул после каждой транзакции, а не после закрытия сессии.
Альтернатива без доп. инфраструктуры — уменьшить `MaxConns` в пуле каждого инстанса:
```
10 инстансов × 5 соединений = 50 соединений к Postgres
```
Оставшиеся соединения Postgres сможет отдать под репликацию и административные задачи. Баланс считается исходя из `max_connections` минус ~10 на системные нужды.
108Можно ли шардирование сделать на одном сервере?
Middle
SQL
Технически — да, практически — нет смысла.
Шардирование разделяет данные между несколькими независимыми узлами, чтобы распределить нагрузку и объём хранилища. Если всё на одном сервере — у вас по-прежнему одно узкое место: CPU, дисковый I/O, RAM.
```
Реальное шардирование:
  shard1 → server A (свой CPU, диск, RAM)
  shard2 → server B (свой CPU, диск, RAM)
"Шарды" на одном сервере:
  shard1 (база prepgo_1) ─┐
  shard2 (база prepgo_2) ─┼── один CPU, один диск
  shard3 (база prepgo_3) ─┘
```
Иногда это делают как подготовительный шаг — чтобы потом легко перенести каждый «шард» на отдельный сервер. Или для логической изоляции данных разных клиентов (multi-tenancy). Но прироста производительности такое «шардирование» не даёт — для этого нужны партиционирование или реплики чтения.
109Что ты можешь рассказать про транзакции в Postgres и MVCC?
Middle
SQL
MVCC (Multiversion Concurrency Control) — механизм, при котором каждая транзакция видит свой снимок (snapshot) базы данных. Вместо блокировок на чтение PostgreSQL хранит несколько версий одной строки.
Каждая строка имеет системные поля `xmin` (ID транзакции, создавшей версию) и `xmax` (ID транзакции, удалившей/обновившей версию). При UPDATE старая версия строки остаётся (с заполненным xmax), новая добавляется рядом.
```
BEGIN; -- транзакция видит снимок на этот момент
SELECT balance FROM accounts WHERE id = 1;
-- → 1000
-- Другая транзакция: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT;
SELECT balance FROM accounts WHERE id = 1;
-- → 1000 (при REPEATABLE READ) или 500 (при READ COMMITTED)
COMMIT;
```
Плюсы MVCC: читатели не блокируют писателей и наоборот — высокий параллелизм. Минус: мёртвые версии строк накапливаются и «раздувают» таблицы (table bloat). Их убирает `autovacuum` — фоновый процесс, который периодически чистит мёртвые строки и обновляет статистику.
110Какие уровни изоляции ты знаешь?
Middle
SQL
SQL-стандарт определяет 4 уровня изоляции и три аномалии, которые они предотвращают:
**Read Uncommitted** — допускает все три аномалии: dirty read, non-repeatable read и phantom read.  
**Read Committed** — предотвращает dirty read, но non-repeatable read и phantom read по-прежнему возможны.  
**Repeatable Read** — предотвращает dirty read и non-repeatable read, но phantom read всё ещё возможен.  
**Serializable** — предотвращает все три аномалии.
В PostgreSQL Read Uncommitted ведёт себя как Read Committed — грязного чтения нет никогда.
Repeatable Read в PostgreSQL также защищает от фантомных чтений (в отличие от стандарта). По умолчанию используется Read Committed.
```
-- Установить уровень для транзакции:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- Или изменить дефолт для сессии:
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```
111Какую проблему решает repeatable read?
Middle
SQL
Repeatable Read решает проблему non-repeatable read — когда одна транзакция читает одну и ту же строку дважды и получает разные данные, потому что другая транзакция успела изменить её между чтениями.
```
-- При Read Committed (поведение по умолчанию):
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- 1000
-- Параллельно: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT;
SELECT balance FROM accounts WHERE id = 1;  -- 500 (значение изменилось!)
COMMIT;
-- При Repeatable Read:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;  -- 1000
-- Параллельно: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT;
SELECT balance FROM accounts WHERE id = 1;  -- 1000 (снимок зафиксирован на момент BEGIN)
COMMIT;
```
Важно для операций, которые читают данные несколько раз и принимают решения на их основе: генерация отчётов, экспорт данных, финансовые расчёты — там, где нужна согласованная картина на момент начала операции. В PostgreSQL Repeatable Read дополнительно защищает от фантомных чтений (phantom read).
112Использовали ли вы где-нибудь нестандартный уровень изоляции?
Middle
SQL
Да. Использовал Repeatable Read для генерации ежедневных финансовых отчётов.
```
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- Оба SELECT видят один снимок данных — отчёт согласован
SELECT SUM(amount) FROM payments
WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02';
SELECT COUNT(*) FROM orders
WHERE status = 'completed'
  AND created_at >= '2024-01-01' AND created_at < '2024-01-02';
COMMIT;
```
Без Repeatable Read два SELECT могли поймать разные наборы данных если транзакции записи шли параллельно — цифры в отчёте не сошлись бы.
Serializable использовал в критичной секции списания баланса, чтобы исключить гонку: два параллельных запроса видят достаточный баланс и оба проходят, хотя должен пройти только один. Serializable обнаруживает такой конфликт и откатывает одну из транзакций с ошибкой `ERROR: could not serialize access`, после чего приложение повторяет попытку.
Важно адаптировать ответ под свою легенду.
113В чем особенности разных видов индексов?
Middle
SQL
**B-tree** (по умолчанию) — универсальный, поддерживает `=`, `<`, `>`, `BETWEEN`, `LIKE 'prefix%'`, `ORDER BY`, `IS NULL`. Подходит для 95% случаев.
```
CREATE INDEX idx_users_email ON users(email);
```
**Hash** — только для точного равенства (`=`), чуть быстрее B-tree для таких запросов. Используется редко — B-tree почти всегда достаточно.
```
CREATE INDEX idx_sessions_token ON sessions USING hash(token);
```
**GIN** (Generalized Inverted Index) — для составных значений: массивы, JSONB, полнотекстовый поиск. Медленная запись, быстрый поиск вхождений оператором `@>`, `&&`, `@@`.
```
CREATE INDEX idx_tags ON articles USING gin(tags);  -- tags: int[]
SELECT * FROM articles WHERE tags @> ARRAY[1, 2];
```
**GiST** — для геометрических типов, диапазонов (`tsrange`, `int4range`), полнотекстового поиска. Используется вместе с PostGIS для геопоиска.
**BRIN** (Block Range Index) — компактный индекс для больших append-only таблиц (логи, события), где строки физически упорядочены по времени. В 100–1000 раз меньше B-tree.
```
CREATE INDEX idx_logs_time ON logs USING brin(created_at);
```
114Что такое частичный индекс в Postgres?
Middle
SQL
Частичный индекс (partial index) — индекс, который строится только по строкам, удовлетворяющим условию WHERE. Остальные строки в индекс не попадают.
```
-- Индекс только по активным заказам (не по всем 10M строк):
CREATE INDEX idx_orders_active ON orders(created_at)
WHERE status = 'active';
```
Плюсы: значительно меньший размер (если «активных» строк 1% — индекс в 100 раз меньше B-tree по всей таблице), быстрее обновляется, лучше помещается в кеш PostgreSQL.
Чтобы планировщик использовал частичный индекс, запрос должен включать то же условие:
```
-- Использует idx_orders_active:
SELECT * FROM orders
WHERE status = 'active' AND created_at > NOW() - INTERVAL '1 day';
-- НЕ использует (нет условия status = 'active'):
SELECT * FROM orders
WHERE created_at > NOW() - INTERVAL '1 day';
```
Другой сценарий — уникальность только среди живых записей:
```
CREATE UNIQUE INDEX idx_users_email_active ON users(email)
WHERE deleted_at IS NULL;
-- Двух активных пользователей с одним email быть не может,
-- но удалённые могут иметь одинаковый email.
```
115Как бы вы расположили поля phone, surname, name в составном индексе и почему?
Middle
SQL
Порядок зависит от того, как поля используются в реальных запросах. Если поиск по всем трём полям через равенство — вперёд ставим поле с наибольшей селективностью (наибольшим числом уникальных значений).
Телефон — как правило уникален для каждого человека (максимальная селективность).  
Фамилия — много повторений (Ивановых в России миллионы).  
Имя — ещё больше повторений.
Если типичный запрос — точный поиск по телефону:
```
CREATE INDEX idx_contacts_phone ON contacts(phone);
-- составной вообще не нужен, телефон уже уникален
```
Если поиск по фамилии + имени (без телефона):
```
CREATE INDEX idx_contacts_name ON contacts(surname, name);
-- surname первым — по нему фильтруем, name сужает выборку
```
Если нужен составной из всех трёх и запросы разные:
```
CREATE INDEX idx_contacts ON contacts(phone, surname, name);
```
Но важно помнить: индекс `(phone, surname, name)` бесполезен для `WHERE surname = 'Иванов'` — без левого поля (phone) индекс не используется. Для разных паттернов запросов нужны разные индексы.
116Можно ли в запросе использовать не все колонки, входящие в составной индекс?
Middle
SQL
Да, можно — но только поля начиная с самого левого (leftmost prefix rule). Можно использовать первые N полей, но нельзя пропускать поля в середине.
```
CREATE INDEX idx ON orders(user_id, status, created_at);
-- Использует индекс (префикс: user_id):
SELECT * FROM orders WHERE user_id = 42;
-- Использует индекс (префикс: user_id + status):
SELECT * FROM orders WHERE user_id = 42 AND status = 'paid';
-- Использует индекс полностью:
SELECT * FROM orders WHERE user_id = 42 AND status = 'paid' AND created_at > '2024-01-01';
-- НЕ использует (пропущен user_id):
SELECT * FROM orders WHERE status = 'paid' AND created_at > '2024-01-01';
```
Если нужно использовать только часть полей правее — помогает отдельный индекс.
Для полей, которые нужны только в SELECT (не в WHERE), используют `INCLUDE` — они не участвуют в фильтрации, но позволяют сделать index-only scan:
```
CREATE INDEX idx ON orders(user_id, status) INCLUDE (total, created_at);
-- total и created_at не влияют на leftmost prefix rule
```
117Как работает leftmost prefix rule у составного индекса?
Middle
SQL
B-tree индекс физически отсортирован по всем полям слева направо. PostgreSQL может «войти» в индекс только с левого конца и использовать поля последовательно. Как только встречается пропуск — дальнейшие поля уже не помогают фильтрации.
```
CREATE INDEX idx ON users(country, city, age);
-- Работает: поиск начинается с country
WHERE country = 'RU'
WHERE country = 'RU' AND city = 'Moscow'
WHERE country = 'RU' AND city = 'Moscow' AND age > 18
-- НЕ работает: country пропущен — Seq Scan
WHERE city = 'Moscow'
WHERE age > 18
-- Частичное использование: country используется, city пропущен → age не помогает
WHERE country = 'RU' AND age > 18
-- индекс сузит выборку до всех 'RU', дальше age фильтруется построчно
```
Для запросов без левых полей нужен отдельный индекс. Порядок полей при создании индекса всегда выбирается исходя из реальных паттернов запросов.
118Как можно масштабировать базу данных?
Middle
SQL
Вертикальное масштабирование (scale up) - добавить CPU, RAM, SSD серверу. Имеет физический потолок.
Репликация чтения — несколько read-реплик принимают SELECT, мастер принимает только запись. Эффективно если нагрузка — преимущественно чтение.
Connection pooling (PgBouncer) — снижает число реальных соединений к Postgres. Повышает производительность без изменения схемы.
Кеширование (Redis) — горячие данные отдаём из кеша, снижая нагрузку на БД.
Партиционирование — большая таблица разбивается на секции по ключу (дата, диапазон ID). Данные остаются на одном сервере, но запросы обходят ненужные партиции.
Шардирование — данные разбиваются между разными серверами. Максимальный горизонтальный масштаб, но сложная реализация: нет JOIN между шардами, нет распределённых транзакций.
Обычно применяют в порядке: кеш → реплики чтения → партиционирование → шардирование.
119Что такое шардирование?
Middle
SQL
Шардирование (sharding) — горизонтальное разбиение данных между несколькими независимыми серверами (шардами). Каждый шард хранит только свою часть данных и обрабатывает только свои запросы.
```
users 1..1 000 000      → shard1 (server A)
users 1 000 001..2 000 000 → shard2 (server B)
users 2 000 001..3 000 000 → shard3 (server C)
```
Ключ шардирования (shard key) — поле, по которому определяется, в какой шард попадёт запись. Выбор ключа критичен: плохой ключ создаёт «горячие» шарды — одни перегружены, другие пустуют.
Ограничения шардирования:  
- JOIN между шардами невозможен — нужно делать в коде приложения.  
- Распределённые транзакции — очень дороги и сложны в реализации.  
- Перешардирование — болезненный процесс перераспределения данных при росте.
В PostgreSQL нативного шардирования нет. Варианты:  
- Citus — расширение, добавляет шардирование поверх PostgreSQL.  
- Шардирование на уровне приложения — роутер определяет нужный инстанс Postgres по ключу и направляет запрос туда.
120Что такое партиционирование?
Middle
SQL
Партиционирование (partitioning) — разделение одной логической таблицы на несколько физических секций (партиций) на одном сервере. Клиентский код работает с одной таблицей как обычно, PostgreSQL сам роутит запросы в нужные партиции.
```
CREATE TABLE events (
    id         BIGSERIAL,
    user_id    INT,
    created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);
CREATE TABLE events_2024_01 PARTITION OF events
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE events_2024_02 PARTITION OF events
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
```
При запросе с условием по ключу партиционирования PostgreSQL обращается только к нужным партициям (partition pruning):
```
-- Читает только events_2024_01, остальные партиции пропускает:
SELECT * FROM events
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01';
```
Плюсы: быстрые запросы по ключу, быстрое удаление старых данных (`DROP TABLE events_2023_01` вместо `DELETE` миллионов строк), удобное обслуживание.
Типы партиционирования в PostgreSQL:  
- `RANGE` — диапазоны (даты, числа) — самый частый случай.  
- `LIST` — перечисление значений (страна, статус).  
- `HASH` — равномерное распределение по хешу ключа.
121Почему партиционирование по первой букве фамилии может быть плохой идеей?
Middle
SQL
**Неравномерное распределение данных.** Буквы в фамилиях распределены крайне неравномерно. Например, на букву «К» или «С» в русскоязычной базе может приходиться 15–20% всех записей, а на «Щ», «Э», «Ю» — доли процента. В итоге одни партиции будут огромными, а другие почти пустыми.
**Hot partition проблема.** Партиция с популярной буквой получает непропорционально большую нагрузку на чтение и запись. Это приводит к неравномерной утилизации дисков, CPU и памяти — часть серверов перегружена, часть простаивает.
**Бесполезность для большинства запросов.** Партиционирование ускоряет запросы только если в `WHERE` есть ключ партицирования. Запросы по `id`, `email`, дате регистрации или любому другому полю будут сканировать **все партиции**, что медленнее, чем одна таблица с нормальным индексом.
**Зависимость от локали.** В разных языках и культурах распределение букв совершенно разное. Если база многоязычная — партиции становятся ещё более перекошенными.
**Что лучше использовать:** партиционирование по **диапазону дат** (если данные хронологические — логи, заказы, события), по **хэшу ID** (если нужно равномерное распределение), или по **статусу/типу** (если есть горячие и холодные данные). Выбор ключа партицирования должен следовать из реальных паттернов запросов, а не из бизнес-атрибутов с произвольным распределением.
122Какие бывают реплики / схемы репликации?
Middle
SQL
**По роли реплик:**
**Primary → Replica (Master-Slave)** — один узел принимает запись, остальные реплики обслуживают чтение. Самая распространённая схема. При падении primary нужен failover — ручной или автоматический (например, через Patroni в PostgreSQL).
**Multi-Primary (Master-Master)** — несколько узлов принимают запись. Сложнее в реализации из-за конфликтов записи. Используется в MySQL Group Replication, CockroachDB, Galera Cluster.
**По способу передачи данных:**
**Синхронная репликация** — primary ждёт подтверждения от реплики перед коммитом транзакции. **Гарантирует** отсутствие потери данных, но увеличивает латентность записи. В PostgreSQL настраивается через `synchronous_commit` и `synchronous_standby_names`.
**Асинхронная репликация** — primary не ждёт реплику, коммит происходит сразу. Быстрее, но при падении primary последние транзакции могут быть **потеряны** (replication lag). Это дефолт в большинстве СУБД.
**Полусинхронная (semi-sync)** — primary ждёт подтверждения хотя бы от одной реплики из нескольких. Компромисс между надёжностью и скоростью. Используется в MySQL Semi-Synchronous Replication.
**По формату передачи:**
**Физическая (WAL-based)** — передаются блоки WAL (Write-Ahead Log). Реплика побайтово идентична primary. Используется в PostgreSQL streaming replication. Быстрая, но реплика должна быть той же версии СУБД.
**Логическая** — передаются логические изменения (INSERT, UPDATE, DELETE). Позволяет реплицировать выборочно (конкретные таблицы), между разными версиями и даже разными СУБД. В PostgreSQL — `PUBLICATION` / `SUBSCRIPTION`. Медленнее физической.
**По топологии:**
**Простая (primary → replicas)** — один primary, одна или несколько реплик. Просто в настройке и обслуживании.
**Каскадная (primary → replica → replica)** — реплика сама является источником для другой реплики. Снижает нагрузку на primary при большом числе реплик.
**Кольцевая (circular)** — каждый узел реплицирует на следующий. Хрупкая схема: падение одного узла ломает цепочку. Практически не используется.
**Что выбрать на практике:** для большинства случаев — **асинхронная физическая primary → replica** с автоматическим failover. Синхронную добавляют, когда потеря даже одной транзакции недопустима (финансы, платежи). Логическую — когда нужна выборочная репликация или миграция между версиями.
123Что нужно делать с кодом и запросами, чтобы реплики приносили пользу?
Middle
SQL
**Разделить чтение и запись на уровне приложения.** Все `INSERT`, `UPDATE`, `DELETE` идут на primary, все `SELECT` — на реплику. В Go это обычно две переменные подключения:
```
primaryDB, _ := pgxpool.New(ctx, "host=primary ...")
replicaDB, _ := pgxpool.New(ctx, "host=replica ...")
```
Сервисный слой выбирает нужный пул в зависимости от операции.
**Учитывать replication lag.** Асинхронная реплика отстаёт на миллисекунды или секунды. Классический баг: пользователь создал заказ (`INSERT` → primary), сразу открывает страницу заказа (`SELECT` → replica) — и не видит его. Решения: для критичных чтений после записи читать **с primary** (read-your-writes), либо добавлять короткую задержку, либо передавать LSN позицию и ждать, пока реплика её догонит.
**Тяжёлые аналитические запросы выносить на реплику.** Отчёты, агрегации, экспорты — всё, что может нагрузить CPU и IO на минуты. На primary такие запросы конкурируют с пользовательскими запросами и могут вызвать деградацию. На реплике они никому не мешают.
**Балансировать нагрузку между репликами.** Если реплик несколько — запросы распределяются через пул соединений (PgBouncer, HAProxy) или на уровне приложения (round-robin). Это горизонтально масштабирует чтение.
**Не отправлять на реплику запросы, требующие строгой консистентности.** Проверка баланса перед списанием, проверка уникальности перед вставкой, чтение текущего статуса для принятия решения — всё это только primary. Иначе race condition из-за лага.
124Какие бывают режимы репликации: синхронная и асинхронная?
Middle
SQL
**Асинхронная репликация** — primary коммитит транзакцию **сразу**, не дожидаясь подтверждения от реплики. WAL-записи отправляются реплике в фоне. Это дефолт в PostgreSQL.
**Плюсы:** минимальная латентность записи, primary не зависит от доступности реплики.   
**Минус:** при падении primary последние транзакции могут быть **потеряны** — они ещё не дошли до реплики. Окно потери — обычно миллисекунды, но при нагрузке может вырасти.
**Синхронная репликация** — primary ждёт подтверждения от реплики **перед** тем как сообщить клиенту об успешном коммите.
**Плюс:** гарантия — если клиент получил «commit ok», данные есть минимум на двух узлах. **Минусы:** латентность записи растёт на время сетевого round-trip до реплики, а если реплика упала — primary **блокирует запись** до её возвращения или до ручного переключения.
**Полусинхронная (semi-synchronous)** — primary ждёт подтверждения от **хотя бы одной** реплики из нескольких. Если одна реплика упала, запись продолжает работать через оставшиеся.
**Что выбрать на практике:** для большинства сервисов — **асинхронная** репликация с автоматическим failover (Patroni). Для финансовых операций, платежей — **полусинхронная** с `ANY 1` и минимум двумя репликами, чтобы не было single point of failure.
125Что делает SELECT ... FOR UPDATE?
Middle
SQL
`SELECT ... FOR UPDATE` блокирует выбранные строки до конца транзакции. Другие транзакции, пытающиеся изменить или заблокировать эти же строки, будут **ждать**.
Основное применение — **предотвращение race condition** при «прочитал → изменил → записал»:
```
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- другие транзакции не смогут изменить эту строку, пока мы не завершим
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```
Без `FOR UPDATE` две параллельные транзакции могут прочитать одинаковый баланс и обе списать деньги — классический lost update.
**`FOR UPDATE NOWAIT`** — не ждёт, а сразу возвращает ошибку, если строка уже заблокирована. Полезно, чтобы не копить ожидающие транзакции.
**`FOR UPDATE SKIP LOCKED`** — пропускает заблокированные строки. Используется для реализации очереди задач: каждый воркер берёт только свободные записи.
126Как обеспечить консистентность при конкурентном чтении/обновлении?
Middle
SQL
**Пессимистичная блокировка** — `SELECT ... FOR UPDATE`. Блокируем строку перед изменением, остальные ждут. Просто и надёжно, но снижает пропускную способность при высокой конкуренции.
**Оптимистичная блокировка** — добавляем колонку `version` или `updated_at`. При обновлении проверяем, что версия не изменилась:
```
UPDATE accounts
SET balance = 500, version = version + 1
WHERE id = 1 AND version = 3;
```
Если `rows affected = 0` — кто-то обновил раньше, повторяем операцию. Хорошо работает, когда конфликты редки.
**Serializable изоляция** — БД сама обнаруживает конфликты. Нужен retry при `serialization_failure`.
**На практике** чаще всего — Read Committed + `FOR UPDATE` для критичных операций, оптимистичная блокировка для остального.
127Что такое оптимистичная блокировка?
Middle
SQL
Подход, при котором мы **не блокируем строку** при чтении, а проверяем при записи, что данные не изменились. Обычно через колонку `version`:
```
-- читаем
SELECT id, balance, version FROM accounts WHERE id = 1;
-- balance=1000, version=3
-- обновляем с проверкой версии
UPDATE accounts
SET balance = 900, version = version + 1
WHERE id = 1 AND version = 3;
```
Если `rows affected = 0` — кто-то обновил строку между нашим чтением и записью. Приложение повторяет операцию с начала.
**Когда подходит:** конфликты редки, большинство операций завершаются успешно с первого раза. Не держим блокировку — другие транзакции не ждут.
**Когда не подходит:** высокая конкуренция за одни и те же строки. Много retry — впустую потраченная работа. В таком случае лучше пессимистичная блокировка через `FOR UPDATE`.
128Что такое пессимистичная блокировка?
Middle
SQL
Подход, при котором мы **блокируем строку сразу при чтении**, не давая другим транзакциям её изменить до конца нашей транзакции. В PostgreSQL — через `SELECT ... FOR UPDATE`:
```
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- строка заблокирована, другие ждут
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
-- блокировка снята
```
**Когда подходит:** высокая конкуренция за одни и те же строки, конфликты частые. Гарантированно нет повторных попыток — транзакция просто ждёт своей очереди.
**Когда не подходит:** низкая конкуренция — блокировки излишни, оптимистичная блокировка будет быстрее. Также при долгих транзакциях — заблокированные строки держат остальных в ожидании, что может привести к очередям и дедлокам.
129Как в EXPLAIN видно, что используется покрывающий индекс?
Middle
SQL
В плане запроса будет **Index Only Scan** вместо обычного Index Scan. Это значит, что все нужные данные есть в индексе и PostgreSQL **не обращается к таблице** (heap).
Выглядит это так:  
`Index Only Scan using idx_orders_user_time on orders`  
`Index Cond: (user_id = 1)`  
`Heap Fetches: 0`
**Heap Fetches: 0** — идеальный случай, данные полностью из индекса. Если значение больше нуля — часть строк всё же читалась из таблицы, обычно из-за того, что `VACUUM` не успел обновить карту видимости.
130Чем отличаются SQL базы данных от NoSQL баз данных?
Middle
SQL
**SQL (реляционные)** — данные в таблицах со строгой схемой, связи через внешние ключи, запросы на SQL. ACID-транзакции, строгая консистентность. Примеры: PostgreSQL, MySQL.
**NoSQL** — общий термин для всего, что не реляционная модель. Гибкая или отсутствующая схема, горизонтальное масштабирование проще. Несколько видов:
**Документные** (MongoDB) — хранят JSON-документы, схема гибкая, каждый документ может отличаться.
**Ключ-значение** (Redis) — простейшая модель, максимальная скорость на точечные чтения по ключу.
**Колоночные** (ClickHouse, Cassandra) — оптимизированы под аналитику или большие объёмы записи.
**Графовые** (Neo4j) — для данных со сложными связями: соцсети, рекомендации.
**Когда SQL:** сложные связи между сущностями, транзакции, консистентность важнее всего.
**Когда NoSQL:** огромные объёмы, гибкая схема, горизонтальное масштабирование важнее строгой консистентности.
На практике часто используют оба: PostgreSQL для основных данных, Redis для кеша, ClickHouse для аналитики.
131Что такое нормализация базы данных?
Middle
SQL
**Нормализация** — процесс организации таблиц так, чтобы убрать дублирование данных и аномалии при вставке, обновлении и удалении.
**Пример без нормализации:** в таблице заказов хранится имя клиента, его адрес и телефон в каждой строке. Клиент сменил адрес — нужно обновить сотни строк. Забыли одну — данные рассогласованы.
**После нормализации:** клиент в отдельной таблице, заказ ссылается на него через `user_id`. Адрес хранится в одном месте, обновляется один раз.
**Когда денормализуют:** когда нужна скорость чтения. Например, в аналитических таблицах или ClickHouse дублирование данных допустимо ради быстрых запросов без JOIN.
132Какие есть нормальные формы базы данных? (про нормализацию)
Middle
SQL
**1NF** — каждая ячейка содержит **одно атомарное значение**. Нет массивов, списков, вложенных таблиц в ячейке. Каждая строка уникальна.
**2NF** — выполнена 1NF + все неключевые поля зависят от **всего составного ключа**, а не от его части. Актуально только для таблиц с составным первичным ключом.
**3NF** — выполнена 2NF + неключевые поля **не зависят друг от друга**, только от первичного ключа. Например, если в таблице заказа хранится `city` и `zip_code`, а город определяется по индексу — это нарушение 3NF. Выносим в отдельную таблицу.
**BCNF (форма Бойса-Кодда)** — ужесточение 3NF. Каждая функциональная зависимость идёт от суперключа. На практике разница с 3NF встречается редко.
**4NF** — нет многозначных зависимостей. Если сущность имеет два независимых набора связей — они в разных таблицах.
**5NF** — нельзя разбить таблицу на более мелкие без потери данных.
**На практике** обычно достаточно **3NF**. Дальше — теоретические формы, которые редко встречаются в реальных проектах.
133Как по схеме БД понять, обязателен ли статус у пользователя?
Middle
SQL
По ограничению **`NOT NULL`**. Если колонка `status` объявлена как `NOT NULL` — значение обязательно, вставить пустую запись без статуса не получится. Если `NOT NULL` нет — колонка допускает `NULL`, статус необязателен.
```
-- обязателен
status varchar(20) NOT NULL
-- необязателен
status varchar(20)
```
Дополнительно может быть **`DEFAULT`** — значение по умолчанию. Тогда поле обязательно на уровне БД, но клиент может не передавать его явно:
```
status varchar(20) NOT NULL DEFAULT 'active'
```
134Для какой самой основной задачи может понадобиться партиционирование таблицы?
Middle
SQL
**Ускорение запросов к большим таблицам с фильтром по дате.** Когда таблица выросла до сотен миллионов строк и большинство запросов берут данные за конкретный период — партиционирование по дате позволяет PostgreSQL сканировать только нужную партицию, а не всю таблицу.
Второй бонус — **быстрое удаление старых данных**. `DROP` партиции за прошлый год — мгновенная операция. `DELETE` миллионов строк — долго и нагружает БД.
135Что происходит при создании индекса через CREATE INDEX на проде, индекс строится сразу или как-то отложенно?
Middle
SQL
**Блокирует запись.** Обычный `CREATE INDEX` берёт блокировку на таблицу — `SELECT` работает, но `INSERT`, `UPDATE`, `DELETE` ждут, пока индекс не построится. На большой таблице это могут быть минуты.
**Решение — `CREATE INDEX CONCURRENTLY`:**
```
CREATE INDEX CONCURRENTLY idx_name ON orders(created_at);
```
Строит индекс в фоне, **не блокируя запись**. Делает два прохода по таблице: первый — собирает данные, второй — подхватывает изменения, которые произошли во время первого. Занимает дольше обычного, но продакшен продолжает работать.
Минусы `CONCURRENTLY`: нельзя запускать внутри транзакции, при ошибке оставляет невалидный индекс (нужно удалить вручную и повторить).
136Что такое vacuum и autovacuum в Postgres?
Middle
SQL
**VACUUM** — процесс очистки «мёртвых» строк. PostgreSQL при `UPDATE` и `DELETE` не удаляет строки физически — старая версия остаётся на месте, помечается как невидимая (из-за MVCC). VACUUM освобождает место, занятое этими мёртвыми строками, для повторного использования.
**AUTOVACUUM** — фоновый процесс, который запускает VACUUM автоматически. Следит за количеством мёртвых строк в каждой таблице и запускает очистку, когда накопилось достаточно. По умолчанию включён.
**Зачем нужен:**
**Раздувание таблиц** — без vacuum таблица растёт в размере, хотя данных не прибавилось. Запросы замедляются, диск заполняется.
**Карта видимости** — vacuum обновляет её, что позволяет Index Only Scan работать без обращения к таблице.
**Предотвращение wraparound** — PostgreSQL использует 32-битные ID транзакций. Без vacuum старые ID не переиспользуются, и при переполнении база **остановится принудительно**.
**VACUUM FULL** — полная перестройка таблицы, освобождает место на диске. Но **блокирует таблицу** на всё время работы. Используется редко, только когда раздувание таблицы критичное.
137Что такое view и materialized view в PostgreSQL?
Middle
SQL
**View** — сохранённый SQL-запрос. Не хранит данные, при каждом обращении выполняет запрос заново. По сути алиас для сложного `SELECT` — удобно для читаемости и переиспользования.
**Materialized View** — сохранённый SQL-запрос **с результатом на диске**. Данные вычисляются один раз и хранятся как таблица. Читается мгновенно, но данные устаревают. Для обновления нужен явный вызов:
```
REFRESH MATERIALIZED VIEW my_view;
```
`CONCURRENTLY` — обновление без блокировки чтения, но требует уникальный индекс на view.
**Когда что:** view — для упрощения запросов, когда скорость не критична. Materialized view — для тяжёлых агрегаций (отчёты, дашборды), которые не нужно считать в реальном времени.
138Как устроен B-tree индекс? В чем сбалансированность B-tree?
Middle
SQL
**B-tree** — дерево, в котором каждый узел содержит **несколько ключей** и указателей на дочерние узлы. В отличие от бинарного дерева, где в узле один ключ и два потомка, в B-tree узел может хранить десятки или сотни ключей.
**Структура:** корень → внутренние узлы → листья. Внутренние узлы содержат ключи-разделители и указатели на дочерние узлы. Листья содержат ключи и ссылки на строки таблицы. В PostgreSQL листья также связаны между собой в цепочку — это ускоряет диапазонные запросы.
**Поиск:** начинаем с корня, сравниваем искомый ключ с разделителями, спускаемся в нужный дочерний узел. На каждом уровне отсекаем огромную часть данных. Для таблицы в миллион строк — обычно 3–4 уровня, то есть 3–4 чтения с диска.
**Сбалансированность** означает, что **все листья находятся на одной глубине**. При вставке, если узел переполняется — он разделяется на два, и средний ключ поднимается в родителя. Если переполняется корень — дерево растёт на один уровень вверх. Благодаря этому путь от корня до любого листа всегда одинаковый — поиск **гарантированно O(log n)** для любого ключа, без вырождения в линейный.

145Что обычно хранят в ClickHouse?
Middle
Clickhouse
**ClickHouse** — колоночная СУБД для аналитики (OLAP). Хранят данные, которые нужно **агрегировать по большим объёмам**, а не читать/обновлять поштучно.

**Почему не PostgreSQL для этого:** запрос «посчитай среднее по 500 млн строк за последний месяц» в PostgreSQL будет работать минуты, в ClickHouse — секунды. Колоночное хранение читает только нужные колонки, а не всю строку целиком.
**Чего в ClickHouse не делают:** частые обновления и удаления отдельных строк, транзакции с ACID-гарантиями, OLTP-нагрузку (много мелких запросов). Для этого остаётся PostgreSQL.
146Почему не использовать ClickHouse везде, если он быстрее?
Middle
Clickhouse
Он быстрее **только для аналитики** — агрегации по миллионам строк. Для всего остального он хуже:
**Нет нормальных UPDATE/DELETE.** Изменение одной строки — тяжёлая операция, перезаписывается целый блок данных. Для OLTP (частые мелкие записи и обновления) это неприемлемо.
**Нет ACID-транзакций.** Нельзя сделать «спиши деньги у одного, начисли другому» атомарно. Для бизнес-логики с консистентностью это не подходит.
**Медленные точечные чтения.** `SELECT * FROM users WHERE id = 1` в PostgreSQL — микросекунды по индексу. В ClickHouse — значительно медленнее, потому что колоночное хранение оптимизировано под сканирование, а не под выборку одной строки.
**Нет внешних ключей и constraints.** Нельзя гарантировать целостность данных на уровне БД.
**Вставка пачками.** ClickHouse эффективен при вставке батчами от тысяч строк. Одиночные инсерты по одной строке — антипаттерн, который создаёт огромный overhead.
**На практике** используют связку: PostgreSQL для OLTP (пользователи, заказы, платежи), ClickHouse для аналитики (отчёты, дашборды, метрики). Данные из PostgreSQL льют в ClickHouse через CDC или батч-процессы.

152Для каких задач используются брокеры сообщений?
Middle
System Design
Брокер сообщений (Kafka, RabbitMQ, NATS) — промежуточный слой для асинхронного обмена данными между сервисами.
**Основные сценарии:**
**Decoupling сервисов** — producer не знает о consumer. Упал consumer — сообщения накапливаются, не теряются.
**Асинхронная обработка** — тяжёлые задачи (генерация отчётов, отправка email, ресайз картинок) уходят в очередь, HTTP-ответ возвращается сразу.

- **NATS** — лёгкий, низкая latency, pub/sub — для микросервисов с простыми требованиями

153Как переписать монолит на микросервисы?
Middle
System Design
Никогда не переписывай всё сразу — это верный путь к провалу. Правильный подход — **постепенная декомпозиция**.
**Стратегия Strangler Fig Pattern:**  
Новые функции сразу пишутся как сервисы. Старый монолит постепенно «задушивается» — функция за функцией вырезается в отдельный сервис.

1. **Нарисуй границы доменов** — где данные и логика не пересекаются  
2. **Выдели самый независимый модуль** — у которого меньше всего связей с остальными  
3. **Создай сервис с собственной БД** — не разделяй базу с монолитом

5. **Удали код из монолита** после стабилизации
**Что усложняет процесс:**  
- **Shared database** — разные сервисы пишут в одни таблицы; нужно разделять данные  
- **Распределённые транзакции** — в монолите одна БД-транзакция, в микросервисах нужна Saga  
- **Тестирование** — интеграционные тесты становятся сложнее
**Когда НЕ стоит:**  
Если монолит работает стабильно и команда маленькая — микросервисы добавят сложности без выгоды. «Модульный монолит» часто лучший компромисс.

**API Gateway** — единая точка входа: аутентификация, rate limiting, routing. Клиент общается с одним адресом, не знает о внутренней топологии.

**Saga** — распределённая транзакция через цепочку событий с компенсирующими действиями при откате.
**Outbox Pattern** — гарантированная публикация события: сначала пишем в БД в одной транзакции с основными данными, потом отдельный воркер отправляет в Kafka. Исключает потерю события при сбое.
**Sidecar** — вспомогательный контейнер рядом с основным (логирование, мониторинг, service mesh proxy).
**CQRS (Command Query Responsibility Segregation)** — разделение операций чтения и записи: разные модели, разные хранилища.
**Retry + Idempotency Key** — повторяем запросы при ошибках, но операция выполняется ровно один раз благодаря уникальному ключу.
**Health Check + Graceful Shutdown** — `/healthz`, `/readyz` для Kubernetes; корректное завершение без потери in-flight запросов.
155Что такое Saga?
Middle
System Design
**Saga** — паттерн управления распределёнными транзакциями в микросервисах. Вместо одной ACID-транзакции — цепочка локальных транзакций, каждая с **компенсирующим действием** при откате.
**Пример: оформление заказа**  
1. Создать заказ → 2. Списать деньги → 3. Зарезервировать товар → 4. Отправить уведомление
Если шаг 3 упал — запускаются компенсации: вернуть деньги → отменить заказ.
**Два вида Saga:**
**Choreography (хореография)** — каждый сервис публикует событие, следующий реагирует. Нет центрального оркестратора.  
- Плюс: слабая связность  
- Минус: сложно отследить общий флоу
**Orchestration (оркестрация)** — центральный оркестратор (Saga Manager) управляет шагами и откатами.  
- Плюс: логика в одном месте, легче дебажить  
- Минус: оркестратор становится точкой отказа
**Важно:**  
- Каждый шаг должен быть **idempotent** — возможен retry  
- Компенсация — это не rollback: данные уже могли быть видны другим  
- Saga обеспечивает **eventual consistency**, не строгую согласованность

157Что такое гексагональная архитектура?
Middle
System Design
**Гексагональная архитектура (Ports and Adapters)** — подход, при котором бизнес-логика находится в центре и не зависит от внешнего мира. Всё внешнее (БД, HTTP, Kafka, внешние API) подключается через **порты** и **адаптеры**.
**Порт** — интерфейс, который определяет домен. Например, `OrderRepository` — это порт. Домен говорит «мне нужно сохранять заказы», но не знает куда.
**Адаптер** — конкретная реализация порта. PostgreSQL-репозиторий, HTTP-хендлер, Kafka-консьюмер — всё это адаптеры. Их можно менять, не трогая бизнес-логику.
**Входящие адаптеры** — то, что вызывает приложение: HTTP-хендлер, gRPC-сервер, CLI-команда.
**Исходящие адаптеры** — то, что приложение вызывает: БД, внешние API, очереди.
По сути это то же самое, что DDD/Clean Architecture — домен в центре, зависимости направлены внутрь. Просто другая терминология и визуализация в виде шестиугольника с портами по граням.
158Чем чистая архитектура отличается от DDD / гексагональной архитектуры?
Middle
System Design
По сути **одна и та же идея** — домен в центре, зависимости направлены внутрь. Различия в терминологии и акцентах:
**Гексагональная (Ports & Adapters)** — фокус на границах приложения. Порты и адаптеры как способ отвязать домен от внешнего мира. Не диктует внутреннюю структуру слоёв.
**Clean Architecture** — фокус на слоях и правиле зависимостей. Чётко выделяет Entities → Use Cases → Interface Adapters → Frameworks. Строгое правило: внутренний слой ничего не знает о внешнем.
**DDD** — фокус на моделировании бизнеса. Добавляет тактические паттерны: сущности, value objects, агрегаты, доменные события, bounded contexts. Это про **как моделировать домен**, а не про слои.
**На практике** их комбинируют: структура слоёв из Clean Architecture, порты и адаптеры из гексагональной, моделирование домена из DDD. В Go-проекте это выглядит одинаково — `domain/`, `application/`, `infrastructure/`, `interfaces/`.
159Чем хореография отличается от оркестрации в паттерне Saga?
Middle
System Design
**Оркестрация** — есть центральный сервис (оркестратор), который управляет всеми шагами саги. Он знает порядок, вызывает каждый сервис по очереди и решает, что делать при ошибке. Логика саги в одном месте — легко понять и отладить. Минус — оркестратор становится точкой отказа и узким местом.
**Хореография** — центра нет. Каждый сервис слушает события и реагирует самостоятельно. Сервис заказов опубликовал «заказ создан» → сервис платежей услышал, списал деньги, опубликовал «оплата прошла» → сервис доставки услышал и начал отгрузку. Логика размазана по сервисам — сложнее отслеживать и дебажить. Зато нет единой точки отказа.
**Когда что:** оркестрация — для сложных саг с множеством шагов и ветвлений. Хореография — для простых цепочек из 2–3 сервисов.
160Что такое ElasticSearch? Как используется?
Middle
System Design
**Elasticsearch** — распределённый поисковой движок на основе Apache Lucene. Хранит данные в виде JSON-документов, индексирует их и обеспечивает **полнотекстовый поиск** с высокой скоростью.

**Полнотекстовый поиск** — поиск по товарам, статьям, документам. Поддерживает морфологию, нечёткий поиск, ранжирование по релевантности.

168Почему Kafka, а не NATS или RabbitMQ?
Middle
Инфраструктура
Выбор зависит от требований. Каждый инструмент имеет свою нишу.
**Kafka выбирают когда:**  
- Нужна высокая пропускная способность (миллионы сообщений/сек)  
- Важно долгосрочное хранение сообщений (retention по времени или объёму)  
- Нужен **replay** — возможность перечитать историю с любого offset  
- Требуется гарантированный порядок внутри партиции  
- Масштабирование консюмеров через consumer groups
**RabbitMQ лучше когда:**  
- Нужна гибкая маршрутизация (exchanges, fanout, topic routing)  
- Паттерн task queue: каждое сообщение обрабатывает ровно один консюмер  
- Важен низкий latency при умеренном объёме  
- DLQ нужна из коробки без ручной реализации
**NATS лучше когда:**  
- Нужен ultra-low latency (< 1мс)  
- Простая pub/sub без строгих гарантий доставки  
- Минимальная инфраструктура: один бинарник, нет ZooKeeper/KRaft
Если нужен audit trail, replay и высокий throughput — Kafka. Для простых воркеров с малым объёмом — RabbitMQ или даже Postgres с `SELECT ... SKIP LOCKED`.
169Что такое Dead Letter Queue (DLQ)?
Middle
Инфраструктура
**Dead Letter Queue (DLQ)** — специальная очередь, куда попадают сообщения, которые не удалось обработать после нескольких попыток retry.
```
Producer → [main-topic] → Consumer
                               │
                     ошибка 3 раза подряд
                               │
                               ▼
                          [main-topic.DLQ]
                               │
                      алерт + ручной разбор
```
**Типичные причины попадания в DLQ:**  
- Невалидный формат сообщения — не десериализуется  
- Бизнес-ошибка: сообщение принципиально не может быть обработано  
- Временная ошибка зависимости после исчерпания retry (здесь лучше exponential backoff)
В **Kafka** DLQ реализуется вручную: при ошибке после N попыток пишем сообщение в отдельный топик `my-topic.DLQ` и коммитим offset основного топика.
В **RabbitMQ** DLQ настраивается нативно через `x-dead-letter-exchange` и `x-message-ttl` на уровне очереди.
DLQ обязательно должна мониториться с алертом. Накопление сообщений в DLQ — сигнал о системной проблеме, требующей расследования.
170Как организовать graceful shutdown в Go-приложении?
Middle
Инфраструктура
```
func main() {
    srv := &http.Server{Addr: ":8080", Handler: router}
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGTERM, syscall.SIGINT)
    go func() {
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatal(err)
        }
    }()
    <-quit // ждём SIGTERM от Kubernetes или SIGINT от Ctrl+C
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    if err := srv.Shutdown(ctx); err != nil {
        log.Printf("shutdown error: %v", err)
    }
    db.Close()       // закрываем пул соединений к БД
    producer.Close() // flush Kafka producer
    log.Println("shutdown complete")
}
```
`srv.Shutdown` перестаёт принимать новые соединения и ждёт завершения активных запросов. Таймаут (30s) — защита от зависших хендлеров.
Kubernetes отправляет **SIGTERM** при удалении пода, затем ждёт `terminationGracePeriodSeconds` (по умолчанию 30s) и убивает SIGKILL. Это значение должно быть больше таймаута shutdown. Без graceful shutdown in-flight запросы получают обрыв соединения.

Число инстансов каждого сервиса смотрел через `kubectl get pods` или в Grafana. Число консюмеров Kafka определяется `replicas` в Deployment и числом партиций в топике — это важно понимать при росте lag'а.

172Принимал ли ты участие в разборе инцидента, когда воркеры не успевали разгребать Kafka?
Middle
Инфраструктура
Да. Обнаружили через алерт на **consumer lag** — он начал расти и не падал. Первым делом открыли Grafana: throughput консюмеров упал, время обработки одного сообщения (p99) выросло в 16 раз.
Оказалось, внешний API, к которому обращался обработчик, начал отвечать медленно: p99 latency вырос с 50мс до 800мс. Консюмер делал этот вызов синхронно на каждое сообщение — пропускная способность упала пропорционально.
**Временное решение:** добавили параллельную обработку внутри консюмера через worker pool — читаем батч, обрабатываем N сообщений параллельно, коммитим после завершения всего батча.
**Долгосрочное решение:** добавили circuit breaker с fallback, таймаут на внешний вызов, кеш для повторяющихся запросов к этому API.
**Постмортем:** зафиксировали RCA, добавили алерт на latency внешнего API как leading indicator — чтобы знать о деградации до того, как lag начинает расти.

174Какие существуют варианты решения проблемы, когда консюмеры Kafka не успевают вычитывать сообщения?

Инфраструктура
Первый шаг — измерить **consumer lag**: разницу между последним offset в партиции и commit offset консюмера.
```

  --describe --group my-group \
  --bootstrap-server kafka:9092
# смотрим колонку LAG
```
**Варианты решения:**

175Может ли помочь увеличение количества консюмеров в consumer group?
Middle
Инфраструктура
Помогает, но **только до числа партиций** в топике. Это жёсткое ограничение Kafka: каждая партиция в один момент назначена ровно одному консюмеру.
```
6 партиций, 3 консюмера → каждый читает по 2 партиции:
  C0 → P0, P3
  C1 → P1, P4
  C2 → P2, P5
6 партиций, 6 консюмеров → максимальный параллелизм:
  C0→P0  C1→P1  C2→P2  C3→P3  C4→P4  C5→P5
6 партиций, 7 консюмеров:
  C0..C5 — как выше
  C6 — простаивает, партиций не хватило
```
Если lag растёт и консюмеров уже столько же сколько партиций — добавление не поможет. Варианты:
- **Увеличить число партиций** — необратимо, требует планирования  
- **Оптимизировать обработчик** — убрать синхронные блокировки, добавить батчинг  
- **Worker pool внутри консюмера** — читать батч и обрабатывать сообщения параллельно
176В чем связь между количеством партиций и количеством консюмеров?
Middle
Инфраструктура
Каждая партиция в один момент времени читается **ровно одним** консюмером внутри consumer group — это жёсткое правило Kafka.
```
Партиции: [P0] [P1] [P2] [P3] [P4] [P5]
3 консюмера:
  C0 читает P0, P3
  C1 читает P1, P4
  C2 читает P2, P5
4 консюмера (партиций 3):
  C0 читает P0
  C1 читает P1
  C2 читает P2
  C3 простаивает — партиций не хватило
```
**Следствия:**  
- Если консюмеров **меньше** чем партиций — один консюмер читает несколько партиций.  
- Если консюмеров **больше** чем партиций — лишние простаивают.  
- **Максимальный параллелизм = число партиций.**
Поэтому при создании топика важно заранее выставить число партиций с запасом на рост. Увеличить партиции можно, уменьшить — нельзя без пересоздания топика.
177Могут ли несколько консюмеров одной consumer group читать одну и ту же партицию?
Middle
Инфраструктура
**Нет.** Это фундаментальная гарантия Kafka — каждая партиция назначается ровно одному консюмеру в рамках одной consumer group. Именно это обеспечивает порядок обработки и отсутствие дублирования при нормальной работе.
Прочитать одну партицию несколькими консюмерами одновременно можно только из **разных** consumer group:
```
Топик: [P0] [P1] [P2]
Group A (сервис аналитики):
  C_a0 → P0, C_a1 → P1, C_a2 → P2
Group B (сервис нотификаций):
  C_b0 → P0, C_b1 → P1, C_b2 → P2
```
Обе группы читают одни и те же партиции **независимо**, каждая со своим offset. Это паттерн **fan-out**: одно событие обрабатывают несколько независимых потребителей — каждый в своей consumer group, без влияния друг на друга.
178Что будет, если накопили большой батч, консюмер умер, а offset уже закоммичен — как не потерять данные?
Middle
Инфраструктура
Это классическая проблема **at-most-once** delivery — коммит до обработки гарантирует потерю данных при краше.
**Решение: коммитить offset только после успешной обработки всего батча.**
```
for {
    msgs, err := reader.FetchMessage(ctx)
    if err != nil {
        break
    }
    if err := processBatch(msgs); err != nil {
        // НЕ коммитим offset — при перезапуске
        // читаем с последнего закоммиченного offset
        log.Printf("batch failed, will retry: %v", err)
        continue
    }
    // коммитим только после успеха
    if err := reader.CommitMessages(ctx, msgs...); err != nil {
        log.Printf("commit failed: %v", err)
    }
}
```
Это даёт **at-least-once** — при краше батч будет обработан повторно. Требует **идемпотентности** обработчика: повторная обработка не должна давать побочных эффектов (проверка по уникальному ID, upsert вместо insert).
**Exactly-once** достигается через Kafka Transactional API (`producer.BeginTransaction()` + `isolation.level=read_committed` у консюмера), но значительно усложняет архитектуру.

183Почему при старте приложения обычно создается один инстанс зависимости на все приложение?
Middle
Инфраструктура
Потому что большинство зависимостей **stateless** или содержат дорогостоящие ресурсы, которые не нужно создавать на каждый запрос.
**Пул соединений к БД** (`*sql.DB`) — открытие соединения стоит 10–50мс + TLS + аутентификация. Один экземпляр переиспользует соединения между всеми запросами. Создание нового `*sql.DB` на запрос исчерпает file descriptors за секунды.
**HTTP-клиент** (`*http.Client`) — содержит внутренний connection pool для keep-alive. Новый клиент на каждый запрос лишает этого преимущества и замедляет работу.
**Логгер** — инициализируется один раз с нужными настройками (level, format, output), затем передаётся через context с добавлением полей (`trace_id`, `user_id`).
**Redis-клиент** — аналогично БД, держит пул соединений к Redis.
Создание нового инстанса на каждый запрос:  
- Замедляет обработку (latency на инициализацию)  
- Исчерпывает ресурсы ОС (fd, memory, tcp connections)

186Как сделать так, чтобы два воркера не взяли одну и ту же задачу?
Middle
Инфраструктура
**Вариант 1: SELECT FOR UPDATE SKIP LOCKED (Postgres)** — атомарный захват задачи:
```
BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;  -- пропускает строки захваченные другими транзакциями
UPDATE jobs
SET status = 'processing', worker_id = $1, started_at = NOW()
WHERE id = $2;
COMMIT;
```
`SKIP LOCKED` гарантирует: два воркера никогда не возьмут одну задачу. Простой и надёжный task queue поверх Postgres без дополнительной инфраструктуры.
**Вариант 2: Redis SET NX** — распределённая блокировка:
```
ok, _ := rdb.SetNX(ctx, "lock:job:"+jobID, workerID, 30*time.Second).Result()
if !ok {
    return // другой воркер уже взял
}
defer rdb.Del(ctx, "lock:job:"+jobID)
```
**Вариант 3: Kafka** — партиция назначена ровно одному консюмеру в group. Гарантирует что одно сообщение обработает ровно один воркер.
Для большинства внутренних task queue проще всего **SELECT FOR UPDATE SKIP LOCKED** — не нужен дополнительный брокер.
187Как сделать так, чтобы задача не пропала, если воркер умер во время выполнения?
Middle
Инфраструктура
Ключевой принцип: **задача считается завершённой только после явного подтверждения**, а не в момент взятия.
**С Postgres task queue — deadline + reaper:**
```
-- Берём задачу с дедлайном
UPDATE jobs
SET status = 'processing',
    started_at = NOW(),
    deadline   = NOW() + INTERVAL '5 minutes',
    worker_id  = $1
WHERE id = $2;
-- После успешной обработки подтверждаем:
UPDATE jobs SET status = 'done' WHERE id = $2;
```
Фоновый **reaper** каждые 30 секунд возвращает зависшие задачи:
```
UPDATE jobs
SET status = 'pending', worker_id = NULL, started_at = NULL
WHERE status = 'processing'
  AND deadline < NOW();
```
Если воркер умер не успев подтвердить — задача вернётся в `pending` по истечении deadline.
**С Kafka:** коммитим offset только **после** успешной обработки. При смерти консюмера Kafka переназначит партицию другому, который перечитает с последнего закоммиченного offset.
Обработчик должен быть **идемпотентным** — повторная обработка одной задачи не должна давать побочных эффектов (проверка по уникальному ID, upsert вместо insert).
188Из каких компонентов состоит кластер Kafka?
Middle
Инфраструктура
**Broker** — основной компонент, хранит партиции топиков, принимает записи от producer, отдаёт консюмерам. Продакшн-кластер обычно 3+ брокеров для репликации и отказоустойчивости.
**Topic / Partition** — топик разбит на партиции, каждая — append-only лог на диске. Партиции реплицируются по брокерам: один брокер является **leader** (принимает запись/чтение), остальные — **followers** (синхронизируют данные).
**Producer** — пишет сообщения в топик. Ключ сообщения определяет партицию через `hash(key) % N`, без ключа — round-robin.
**Consumer / Consumer Group** — читает партиции. Группа обеспечивает распределение партиций между консюмерами и хранит commit offset.
**ZooKeeper / KRaft** — раньше Kafka использовала ZooKeeper для хранения метаданных и выборов лидеров партиций. С Kafka 3.x переходят на встроенный **KRaft** (Kafka Raft Metadata) — ZooKeeper больше не требуется.
**Schema Registry** (опционально, Confluent) — централизованное хранение Avro/Protobuf схем. Producer регистрирует схему, консюмер валидирует по ней десериализацию.
189Что вызывает ребалансировку consumer group?
Middle
Инфраструктура
**Ребалансировка** — процесс перераспределения партиций между консюмерами в group. Во время ребалансировки обработка сообщений приостанавливается.
**Причины ребалансировки:**  
- Новый консюмер присоединился к group (scale up)  
- Консюмер упал или перестал слать heartbeat в течение `session.timeout.ms`  
- Консюмер слишком долго обрабатывает батч и не успевает вызвать `poll()` — превышен `max.poll.interval.ms`  
- Добавлены новые партиции в топик  
- Перезапуск пода в Kubernetes
**Как минимизировать ребалансировки:**
1. Тюнинг таймаутов: `heartbeat.interval.ms` (3s) < `session.timeout.ms` (30–45s), а `max.poll.interval.ms` — с запасом относительно реального времени обработки батча.
2. **Static membership** (`group.instance.id`) — при перезапуске консюмер получает обратно те же партиции без ребалансировки всей группы.
3. **Cooperative rebalancing** (Kafka 2.4+) — инкрементальная ребалансировка: консюмер отдаёт только «лишние» партиции, остальные продолжают обрабатываться без паузы.
190Можно ли использовать health check / service discovery для отслеживания умерших воркеров?
Middle
Инфраструктура
Да, это стандартная практика. Kubernetes использует **liveness probe** для обнаружения зависших или упавших контейнеров:
```
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 15
  failureThreshold: 3   # 3 неудачи подряд → перезапуск пода
```
Если воркер перестаёт отвечать — Kubernetes перезапускает контейнер. Задачи, которые воркер обрабатывал, должны быть подхвачены через deadline/reaper (Postgres) или через ребалансировку (Kafka).
**Service discovery (Consul / Kubernetes endpoints)** позволяет coordinator-сервису видеть список живых воркеров. Если воркер пропал из registry — coordinator перераспределяет его задачи.
**Kafka** делает это автоматически через **heartbeat**: если консюмер перестаёт слать heartbeat в течение `session.timeout.ms` — Kafka исключает его из consumer group и запускает ребалансировку. Партиции переходят к живым консюмерам без ручного вмешательства.
**Readiness probe** дополнительно защищает от отправки трафика на под, который ещё не прогрелся или временно не готов (например, перестраивает кеш).
191Как инвалидировать in-memory cache, если запрос на мутацию попал только в один под, а кэш хранится локально в каждом поде?
Middle
Инфраструктура
Проблема: мутация пришла на `pod-1`, он инвалидировал свой локальный кеш, но `pod-2` и `pod-3` продолжают отдавать устаревшие данные.
**1. Pub/Sub через Redis** — самый распространённый подход. После мутации pod-1 публикует событие, все поды подписаны и инвалидируют свой кеш:
```
// После мутации:
rdb.Publish(ctx, "cache:invalidate", userID)
// При старте каждого пода:
sub := rdb.Subscribe(ctx, "cache:invalidate")
go func() {
    for msg := range sub.Channel() {
        localCache.Delete(msg.Payload)
    }
}()
```
**2. Короткий TTL** — in-memory кеш живёт 5–30 секунд. Просто в реализации, но данные гарантированно устаревшие в пределах TTL.
**3. Только Redis, без in-memory** — единый источник правды, нет проблемы синхронизации. Теряем скорость локального кеша (Redis ~0.3ms vs in-memory ~0.001ms).
**4. Consistent hashing / sticky routing** — запросы по конкретному ключу всегда идут на один под. Один под — один кеш — нет расхождения. Сложнее реализовать на уровне Ingress/Service Mesh.
На практике чаще всего используют комбинацию: in-memory с коротким TTL (5–10s) + Redis pub/sub для немедленной инвалидации.
192Как синхронизировать кэш между несколькими инстансами?
Middle
Инфраструктура
**Вариант 1: Redis как единый источник правды** — самый простой:
```
val, err := rdb.Get(ctx, "user:42").Result()
// нет in-memory кеша, всегда идём в Redis (~0.3мс)
```
Нет проблемы синхронизации. Минус: каждый запрос = сетевой вызов в Redis.
**Вариант 2: in-memory + Redis Pub/Sub** — двухуровневый кеш:
```
// После мутации публикуем событие инвалидации:
rdb.Publish(ctx, "cache:invalidate", "user:42")
// Каждый под подписан при старте:
sub := rdb.Subscribe(ctx, "cache:invalidate")
go func() {
    for msg := range sub.Channel() {
        localCache.Delete(msg.Payload) // мгновенная инвалидация
    }
}()
```
Быстрое чтение из памяти (~0.001мс), мгновенная инвалидация по всем подам при мутации.
**Вариант 3: короткий TTL без явной инвалидации**:
```
localCache.Set("user:42", data, 10*time.Second)
```
Просто, но данные могут быть устаревшими до истечения TTL.
На практике: для read-heavy данных с редкими мутациями — **вариант 2**. Для данных где важна немедленная свежесть — только Redis. Для статичных данных (конфиги, справочники) — вариант 3 с TTL 1–5 минут.
193Есть ли у вас дежурства? Как устроены?
Middle
Инфраструктура
В зрелых командах дежурства (on-call) организованы ротационно: один инженер дежурит неделю, затем передаёт вахту следующему.
**Типичная организация:**  
- Ротация через PagerDuty или Opsgenie — расписание на месяц вперёд  
- **Primary on-call** получает алерт, **secondary** — если primary не ответил за N минут  
- SLA на ответ: P1 (прод упал) — 5 минут, P2 (деградация) — 30 минут  
- Runbook для каждого алерта: что смотреть и что делать
**Что входит в дежурство:**  
- Реакция на алерты в нерабочее время  
- Участие в постмортеме по инцидентам своей недели  
- Улучшение runbook если что-то оказалось недокументированным
**Важные принципы:**  
- Дежурный не должен тратить ночь на непонятные алерты — runbook даёт чёткий план  
- Если алерт сработал и оказался ложным — задача следующей рабочей недели: улучшить алерт  
- Постмортемы без blame-культуры: ищем системную причину, не виноватого
194Как часто проходят релизы? Есть ли релизный календарь?
Middle
Инфраструктура
Зависит от зрелости команды и типа продукта.
**Continuous Delivery** — деплой в prod при каждом мерже в `main`, если все тесты прошли. Характерно для SaaS с хорошим тестовым покрытием и feature flags. Деплой происходит несколько раз в день автоматически.
**Регулярные релизы** — раз в неделю или раз в две недели. Команда накапливает фичи в release-ветке, проводит регрессию, деплоит в начале буднего дня. Есть релизный календарь с freeze-периодом за день до деплоя.
**Feature flags** позволяют деплоить код не выкатывая фичу пользователям — новый код в проде, флаг выключен. Включают постепенно: 5% → 20% → 100%. Это позволяет деплоить чаще и снижает риск.
**Хорошие практики:**  
- Деплоить утром буднего дня — вся команда онлайн и может быстро откатить  
- Не деплоить в пятницу вечером и перед праздниками  
- Каждый деплой тегируется версией и SHA коммита — легко откатить `kubectl rollout undo`
195Многослойное кэширование для высоконагруженных эндпоинтов. Опиши слои: что лежало в in-memory, а что в Redis?
Middle
Инфраструктура
**In-memory кеш** (fastcache, sync.Map, ristretto) — данные которые:  
- Читаются тысячи раз в секунду  
- Меняются редко (справочники, конфиги, feature flags, permission matrix)  
- Небольшой объём — умещаются в RAM каждого пода  
- Допускают eventual consistency на время короткого TTL (5–30s)
Примеры: список категорий товаров, курсы валют, конфиг приложения, список стран.
**Redis** — данные которые:  
- Должны быть видны всем инстансам немедленно после мутации  
- Требуют явной инвалидации по событию  
- Большой объём — не влезают в RAM каждого пода  
- Требуют TTL с точным expire (сессии, OTP-коды)
Примеры: сессии пользователей, корзина покупок, результаты дорогих SQL-запросов, rate limiting счётчики.
**Схема запроса (cache-aside):**
```
1. Проверяем in-memory кеш → HIT → return (0.001мс)
2. Проверяем Redis         → HIT → обновляем in-memory → return (0.3мс)
3. Идём в БД               → обновляем Redis → обновляем in-memory → return (5–50мс)
```
При мутации: инвалидируем Redis, рассылаем Pub/Sub событие всем подам для инвалидации их in-memory кешей.
196Как решал вопрос обратной совместимости при изменении схем в proto-файлах?
Middle
Инфраструктура
Protobuf хорошо поддерживает обратную совместимость при соблюдении правил.
**Безопасные изменения:**
```
message User {
  int32  id    = 1;
  string name  = 2;
  string email = 3;  // добавить новое поле — всегда OK
}
```
- **Добавить поле** — старые клиенты игнорируют неизвестные поля  
- **Переименовать поле** — безопасно (proto использует номера, не имена)  
- **Пометить поле deprecated** — предупреждение без поломки
**Нельзя:**
```

string id = 1;  // было int32
// НЕЛЬЗЯ: переиспользовать номер удалённого поля
reserved 3;     // поле было удалено — номер бронируем навсегда
reserved "phone";
```
**При breaking changes — версионирование пакета:**
```
api/v1/user.proto  → поддерживаем параллельно
api/v2/user.proto  → новая версия с изменениями
```
197Какими видами тестирования занимался и какие знаешь?
Middle
Инфраструктура
**Unit-тесты** — тестируем отдельную функцию/метод в изоляции. Зависимости заменяются моками. Быстрые (миллисекунды), запускаются на каждый коммит в CI.
**Интеграционные тесты** — проверяем взаимодействие с реальными зависимостями (БД, Redis). В Go используют `testcontainers-go`:
**E2E тесты** — проверяем систему целиком через HTTP/gRPC API. Медленные, запускаются реже — перед релизом.

199Что такое табличное тестирование?
Middle
Инфраструктура
**Table-driven tests** — паттерн в Go, где несколько тест-кейсов описываются в виде таблицы (слайс структур), а один цикл прогоняет их все.
```
func TestDivide(t *testing.T) {
    tests := []struct {
        name    string
        a, b    float64
        want    float64
        wantErr bool
    }{
        {"positive", 10, 2, 5, false},
        {"negative", -6, 2, -3, false},
        {"zero divisor", 10, 0, 0, true},
        {"float", 7, 2, 3.5, false},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := Divide(tt.a, tt.b)
            if (err != nil) != tt.wantErr {
                t.Fatalf("unexpected error: %v", err)
            }
            if got != tt.want {
                t.Errorf("got %v, want %v", got, tt.want)
            }
        })
    }
}
```
`t.Run` создаёт подтест — запускать можно выборочно: `go test -run TestDivide/zero_divisor`.
**Преимущества:**  
- Легко добавить новый кейс — одна строчка в таблице, не нужна новая функция  
- Нет дублирования кода  
- Вывод чётко показывает какой именно кейс упал  
- Паттерн рекомендован в официальной документации Go
200К тебе прибежал менеджер: в программе ошибка, есть логи. Какие твои действия?
Middle
Инфраструктура
**Шаг 1: Оценить важность проблемы.** Прод упал или деградирует? Если упал — делаем роллбек, разбор потом. Если деградирует частично — есть время разобраться.
**Шаг 2: Найти `trace_id` в логах** и открыть трейс в Jaeger/Tempo — сразу видно где и на каком сервисе сломалось.
**Шаг 3: Выяснить когда появилось.** Был ли деплой незадолго до ошибки? Если да — `git log` за этот период, смотрим изменения.
**Шаг 4: Воспроизвести локально.** Взять входные данные из логов, запустить сервис локально с теми же данными.
**Шаг 5: Исправить и написать тест.** После фикса добавить тест который воспроизводит именно этот кейс — чтобы не повторилось.
**Чего не делать:**  
- Не трогать production данные напрямую без согласования

201Когда стоит применять gRPC, а когда REST в контексте микросервисов?
Middle
Инфраструктура
**gRPC выбирают когда:**  
- Внутреннее межсервисное взаимодействие — клиент известен, не нужна универсальность  
- Важна производительность: Protobuf в 5–10 раз компактнее JSON, бинарный протокол быстрее  
- Нужен строгий контракт — `.proto`-файл как единый источник правды, кодогенерация клиентов для Go, Python, Java  
- Bidirectional streaming — gRPC поддерживает из коробки (REST — нет)  
- Высокий RPS между сервисами — connection multiplexing поверх HTTP/2
**REST выбирают когда:**  
- Публичное API — клиент неизвестен, важна простота интеграции из браузера, curl, Postman  
- Нужен human-readable формат — JSON легко читать и дебажить без специальных инструментов  
- Простота: не нужны proto-файлы, кодогенерация, настройка Protobuf  
- Webhooks и интеграции с третьими сторонами — они ожидают HTTP+JSON
**На практике:** внутри кластера — gRPC, публичный API и webhooks — REST.
**gRPC-Gateway** — промежуточный вариант: один `.proto`-файл, и сервис одновременно отдаёт gRPC для внутренних клиентов и REST/JSON для внешних.
202Какие HTTP-методы знаешь?
Middle
Инфраструктура
**Основные методы и их семантика:**
**GET** — получить ресурс. Идемпотентен.
**POST** — создать ресурс или выполнить действие. **Не идемпотентен**.
**PUT** — полностью заменить ресурс. Идемпотентен.
**PATCH** — частично обновить ресурс. **Не идемпотентен**.
**DELETE** — удалить ресурс. Идемпотентен.
**HEAD** — как GET, но без тела ответа. Идемпотентен.
**OPTIONS** — узнать разрешённые методы (CORS preflight). Идемпотентен.
**Идемпотентность** — повторный запрос с теми же данными даёт тот же результат. `PUT /users/1` с одним телом всегда оставит пользователя в одном состоянии. `POST /users` дважды создаст двух пользователей.
**PUT vs PATCH**: `PUT` заменяет всю запись целиком (нужно передать все поля), `PATCH` обновляет только переданные поля. В REST API `PATCH` удобнее для частичных обновлений, `PUT` — для полной замены.
**POST vs PUT**: `POST` на коллекцию создаёт новый ресурс с ID, назначенным сервером. `PUT` на конкретный ID создаёт или заменяет ресурс с заданным ID.
Следует помнить что вышеописанное это в идеальном мире, в реальности могут быть и все операции через пост, и как угодно.
203Какие ключевые различия между HTTP/1.1, HTTP/2 и HTTP/3?
Middle
Инфраструктура
**HTTP/1.1** — каждый запрос обрабатывается последовательно в TCP-соединении. Head-of-line blocking: один зависший запрос блокирует все последующие. Заголовки текстовые, не сжимаются. Браузеры открывают 6–8 параллельных соединений как воркэраунд.
**HTTP/2** решает эти проблемы:  
- **Мультиплексирование** — несколько запросов и ответов параллельно в одном TCP-соединении, без очереди  
- **HPACK** — сжатие заголовков, повторяющиеся заголовки передаются один раз  
- **Binary protocol** — эффективнее текстового HTTP/1.1  
- **Server Push** — сервер отправляет ресурс до того как клиент его запросит
Минус HTTP/2: head-of-line blocking остаётся на уровне **TCP** — потеря одного пакета блокирует все потоки мультиплексора.
**HTTP/3** устраняет это:  
- Работает поверх **QUIC** (UDP) вместо TCP  
- Мультиплексирование без head-of-line blocking на транспортном уровне  
- Встроенный TLS 1.3, **0-RTT** при повторном подключении  
- Лучше работает при потерях пакетов (мобильные сети, Wi-Fi)
```
HTTP/1.1:  [req1]──[resp1]──[req2]──[resp2]  (очередь)
HTTP/2:    [req1]──────────────[resp1]
           [req2]──────[resp2]               (одно TCP, параллельно)
HTTP/3:    [req1]──────────────[resp1]
           [req2]──────[resp2]               (QUIC/UDP, независимые потоки)
```

207Какую версию Go используете?

```

208Как вы решаете, когда переходить на новую версию Go?
Middle
Инфраструктура
Переход обычно происходит через **1–3 месяца после выхода новой версии** — ждём первый патч-релиз (1.23.1, 1.23.2), который фиксит баги, обнаруженные сразу после релиза.
**Триггеры для немедленного обновления:**  
- **Security fix** — обновляем как можно скорее, безопасность важнее стабильности  
- Текущая версия вышла из поддержки (Go поддерживает только 2 последних релиза)
**Триггеры для планового обновления:**  
- Нужна фича из новой версии (например, `slog` в 1.21, `range over func` в 1.23)  
- Улучшения производительности рантайма (GC, компилятор)
**Процесс обновления:**
```
# 1. Обновить go.mod и пересобрать зависимости
go mod tidy
# 2. Статический анализ
go vet ./...
# 3. Тесты с race detector
go test -race ./...
# 4. Обновить Dockerfile и CI
# FROM golang:1.23-alpine → FROM golang:1.24-alpine
# 5. Задеплоить в staging, наблюдать метрики 1–2 дня
```
Go очень хорошо соблюдает **обратную совместимость** — код написанный для Go 1.0 компилируется в Go 1.24. Поэтому обновление почти никогда ничего не ломает.

210Чем Docker отличается от Docker Compose?
Middle
Инфраструктура
**Docker** — запускает **один контейнер** из одного образа. Одна команда `docker run` — один процесс.
**Docker Compose** — запускает **несколько контейнеров** разом по описанию в `docker-compose.yml`. Поднимает целое окружение: БД, кэш, брокер очередей, сам сервис — одной командой `docker compose up`.
Compose также настраивает **общую сеть** между контейнерами, порядок запуска (`depends_on`), тома для хранения данных и переменные окружения. По сути это оркестратор для локальной разработки.
211Что происходит, когда Docker контейнер останавливают?
Middle
Инфраструктура
Docker отправляет главному процессу контейнера (PID 1) сигнал **SIGTERM**. Процесс получает возможность завершиться корректно — закрыть соединения, дописать данные, отправить ответы.
Если процесс не завершился за **10 секунд** (по умолчанию, настраивается через `--stop-timeout`), Docker отправляет **SIGKILL** — принудительное завершение без возможности обработки.
Поэтому важно реализовывать **graceful shutdown** — ловить SIGTERM и корректно завершать работу.
212Что такое volume в Docker? Чем это отличается от container?
Middle
Инфраструктура
**Volume** — это хранилище данных, которое живёт **отдельно от контейнера**. Контейнер удалили — volume остался, данные на месте.
**Контейнер** состоит из **слоёв образа** (read-only) и одного **записываемого слоя** сверху. Слои образа — это результат каждой инструкции в Dockerfile (`FROM`, `RUN`, `COPY`). Они неизменяемые и переиспользуются между контейнерами. Записываемый слой — то, что контейнер меняет во время работы (логи, временные файлы). При удалении контейнера (`docker rm`) этот записываемый слой **пропадает**.
Volume подключается к контейнеру как директория:
```
services:
  postgres:
    image: postgres:16
    volumes:
      - pg_data:/var/lib/postgresql/data
volumes:
  pg_data:
```
Здесь `pg_data` — volume, который сохраняет данные PostgreSQL между перезапусками и пересозданиями контейнера.
**Итого:** слои образа — неизменяемые, общие между контейнерами. Записываемый слой — временный, умирает вместе с контейнером. Volume — постоянное хранилище, которое переживает контейнер.
213В каком контексте вообще хранится offset в Kafka?
Middle
Инфраструктура
Offset хранится в **внутреннем топике `__consumer_offsets`** на стороне Kafka. Каждая consumer group периодически коммитит туда свою позицию — какое последнее сообщение было обработано в каждом партишене.
При перезапуске консьюмер читает свой последний закоммиченный offset из этого топика и продолжает с того места, где остановился.
**Auto-commit** — по умолчанию offset коммитится автоматически каждые 5 секунд. Это значит, что при падении консьюмера между коммитами часть сообщений может быть обработана повторно.
**Manual commit** — коммитим offset явно после успешной обработки. Надёжнее, но нужно самому следить за вызовом коммита.
214Чем чтение Kafka с group\_id отличается от чтения без group\_id?
Middle
Инфраструктура
**С `group_id`** — консьюмер входит в consumer group. Kafka **автоматически распределяет** партишены между консьюмерами в группе — каждый партишен читает только один консьюмер. Offset хранится в `__consumer_offsets`, при перезапуске чтение продолжается с последней позиции.
**Без `group_id`** — консьюмер подписывается на конкретные партишены вручную (`assign`). Никакого автоматического распределения нет, offset нигде не хранится — нужно самому отслеживать позицию. Обычно используется для служебных сценариев: мониторинг, дебаг, перечитывание данных с начала.
215Как бы ты решал проблему, когда связанные события в Kafka приходят из разных партиций и нарушают порядок обработки?
Middle
Инфраструктура
**Партицирование по ключу** — самое простое решение. Все события одной сущности отправлять с одним ключом (например, `user_id`). Kafka направит их в один партишен, порядок гарантирован.
**Если разные топики — буферизация на стороне консьюмера.** При получении `UserUpdate` проверяем, есть ли пользователь в базе. Если нет — откладываем событие в отдельную очередь (retry-топик или локальный буфер) и обрабатываем позже.
**Идемпотентная обработка с версией.** Каждое событие несёт `version` или `timestamp`. Консьюмер применяет только если версия новее текущей в базе. Старые события просто игнорируются.
**Upsert вместо строгого create/update.** Если `UserUpdate` пришёл первым — делаем `INSERT ON CONFLICT DO UPDATE`. Когда позже придёт `UserCreate` — он ничего не сломает, потому что запись уже существует.
**На практике** лучше всего не допускать проблему — партицировать по ключу сущности и держать связанные события в одном топике.
216Из чего состоит сообщение в Kafka, кроме payload?
Middle
Инфраструктура
**Key** — ключ сообщения. Определяет, в какой партишен попадёт сообщение. Сообщения с одинаковым ключом всегда идут в один партишен.
**Value** — само тело сообщения (payload).
**Headers** — набор пар ключ-значение для метаданных. Например, тип события, идентификатор трейса, версия схемы.
**Timestamp** — время создания сообщения. Может быть выставлено продюсером или назначено брокером, зависит от настройки топика.
Эти данные тоже есть в сообщении, но их добавляет сам брокер.
**Offset** — порядковый номер сообщения внутри партишена. Назначается Kafka автоматически при записи.
**Partition** — номер партишена, в который попало сообщение.
**Topic** — имя топика, к которому относится сообщение.
217Что такое гистограмма (histogram) в Prometheus?
Middle
Инфраструктура
В Prometheus **histogram** — это метрика, которая распределяет значения по корзинам. Чаще всего используется для замера **латентности запросов**.
Например, задаём корзины: 10ms, 50ms, 100ms, 500ms, 1s. Prometheus считает, сколько запросов попало в каждую корзину. Из этого можно вычислить **перцентили** — например, p99 (99% запросов быстрее какого значения).
218Что такое counter в Prometheus?
Middle
Инфраструктура
**Counter** — метрика, которая только растёт. Никогда не уменьшается, сбрасывается только при перезапуске сервиса.
Используется для подсчёта событий: количество запросов, количество ошибок, количество обработанных сообщений.
```
requestsTotal := prometheus.NewCounter(prometheus.CounterOpts{
    Name: "http_requests_total",
})
requestsTotal.Inc() // +1 при каждом запросе
```
Само по себе абсолютное значение счётчика не очень полезно. В Grafana используют функцию `rate()` — она показывает **скорость роста** за период. Например, `rate(http_requests_total[5m])` — среднее количество запросов в секунду за последние 5 минут.
219Что знаешь про Prometheus / Grafana / метрики?
Middle
Инфраструктура
**Prometheus** — система мониторинга, которая **сама ходит** в сервисы и забирает метрики (pull-модель). Сервис выставляет эндпоинт `/metrics`, Prometheus периодически его скрейпит и сохраняет данные во внутреннюю time-series БД.
**Grafana** — визуализация. Подключается к Prometheus как источнику данных и строит дашборды с графиками. Там же настраиваются алерты — например, «если p99 латентность выше 500ms дольше 5 минут — отправь в Slack».
**Основные типы метрик:**
**Counter** — только растёт. Количество запросов, ошибок, обработанных сообщений. Полезен через `rate()`.
**Gauge** — может расти и падать. Текущее количество горутин, соединений в пуле, размер очереди.
**Histogram** — распределение значений по корзинам. Латентность запросов, размеры ответов. Из него считают перцентили.
**На практике** минимальный набор метрик для сервиса: количество запросов (`counter`), латентность (`histogram`), количество ошибок (`counter`), размер пула соединений и очередей (`gauge`). Этого достаточно, чтобы быстро находить проблемы.
220Что такое gRPC?
Middle
Инфраструктура
**gRPC** — фреймворк для удалённого вызова процедур от Google. Сервис вызывает метод другого сервиса как обычную функцию, а gRPC берёт на себя сериализацию, транспорт и десериализацию.
**Контракт** описывается в `.proto` файле, из него генерируется код клиента и сервера для любого языка.
**Под капотом** использует HTTP/2 (мультиплексирование, сжатие заголовков) и Protocol Buffers (бинарная сериализация — компактнее и быстрее JSON).
**Четыре типа взаимодействия:** unary (запрос-ответ), server streaming (сервер шлёт поток), client streaming (клиент шлёт поток), bidirectional streaming (поток в обе стороны).
**Когда используют:** межсервисное общение внутри кластера, где важна скорость и строгий контракт. Для внешнего API обычно остаётся REST — браузеры и мобильные клиенты работают с ним проще.
221С какими проблемами приходилось сталкиваться при деплое?
Middle
Инфраструктура
**Миграции ломают старую версию.** Деплой идёт rolling update — какое-то время работают и старые, и новые поды. Если миграция удалила колонку, старая версия падает. Решение — двухэтапные миграции: сначала деплоим код, который не использует колонку, потом удаляем её.
**Readiness probe не настроена.** Kubernetes начинает слать трафик на под, который ещё не готов — не поднял соединение к БД или не прогрел кеш. Пользователи получают ошибки.
**Нехватка ресурсов.** Новая версия потребляет больше памяти, pod уходит в OOMKill. Или CPU limits слишком низкие — под тротлится и отвечает медленно. Решение — нагрузочное тестирование перед релизом, адекватные requests/limits.
**Забытые переменные окружения.** Новая версия ожидает переменную, которую не добавили в конфиг окружения. Сервис падает при старте. Решение — проверка обязательных переменных при инициализации с понятным сообщением об ошибке.
**Долгий graceful shutdown.** При деплое старый под получает SIGTERM, но не успевает завершить текущие запросы за отведённое время. Kubernetes убивает его через SIGKILL. Решение — настроить `terminationGracePeriodSeconds` и корректно обрабатывать сигналы в коде.
222В какой структуре хранятся данные в Redis?
Middle
Инфраструктура
Redis хранит данные в **хэш-таблице** в оперативной памяти. Все данные — это пары ключ-значение, где ключ всегда строка, а значение может быть разных типов:
**String** — простое значение, число или строка. Самый базовый тип.
**Hash** — вложенная хэш-таблица. Удобно для объектов: `HSET user:1 name "John" age 30`.
**List** — двусвязный список. Быстрая вставка в начало и конец, используется для очередей.
**Set** — множество уникальных значений. Поддерживает пересечения, объединения.
**Sorted Set (ZSet)** — множество с весом у каждого элемента. Автоматически отсортировано по весу. Используется для рейтингов, лидербордов.
**Stream** — лог событий, похож на Kafka-топик. Поддерживает consumer groups.
Всё хранится **в памяти**, поэтому быстро.
Также Redis может писать на диск.

223Что такое идемпотентность запроса? Как реализовать идемпотентность запроса?
Middle
Инфраструктура
**Идемпотентность** — повторный запрос с теми же данными даёт тот же результат и не создаёт побочных эффектов. Один раз вызвал или десять — состояние системы одинаковое.
**Как реализовать:**
**Idempotency Key** — клиент передаёт уникальный ключ в заголовке (например, `Idempotency-Key: uuid`). Сервер при первом запросе сохраняет ключ и результат, при повторном — возвращает сохранённый результат без повторного выполнения.
**Уникальные ограничения в БД** — `UNIQUE` constraint не даст создать дубликат. Повторный `INSERT` получит ошибку, которую обрабатываем как «уже создано».
**Естественная идемпотентность** — некоторые операции идемпотентны сами по себе. `PUT` с полной заменой ресурса, `DELETE` по ID — повторный вызов не меняет состояние.
**На практике** для платежей и критичных операций используют Idempotency Key + сохранение результата в БД в одной транзакции с основной операцией.

227Что делать, если микросервис со временем начинает зависать и его приходится перезапускать?
Middle
Инфраструктура
**Найти причину**. Типичные виновники:
**Утечка горутин** — горутины создаются, но не завершаются. Копятся и едят память. Диагностика: `pprof` эндпоинт `/debug/pprof/goroutine`, смотреть количество горутин со временем.

**Как защититься:** liveness probe в Kubernetes — если сервис не отвечает, под автоматически перезапустится. Но это костыль — параллельно нужно искать и устранять корневую причину.
228Kafka распределяет партиции между консюмерами или это делает клиент Kafka?
Middle
Инфраструктура
**Kafka-брокер координирует**, но распределение считает **клиентская библиотека**.
Работает так: один из брокеров назначается **координатором группы** (group coordinator). Когда консьюмер подключается или отключается, координатор инициирует **rebalance**. Middle

238Что такое DNS и как он работает?
Middle
Сеть
DNS (Domain Name System) — распределённая иерархическая система, которая резолвит доменные имена в IP-адреса.
Как работает запрос.
```
ОС проверяет локальный кеш и /etc/hosts
Отправляет запрос к recursive resolver (роутер или 8.8.8.8)
Resolver не знает → запрашивает root nameserver (знает адреса TLD-серверов)
Root возвращает адрес TLD nameserver для .com

```

239Что такое атака Man-in-the-Middle (MITM)?

242Что такое CSRF-атака и как от неё защититься?
Middle
Сеть

Проверка Origin/Referer заголовков.

244Что такое SQL-инъекция и как её можно осуществить?
Middle
Сеть

**Как работает**
Уязвимый запрос:
```
query := "SELECT * FROM users WHERE username = '" + username + "'"
```
Атакующий передаёт в `username` значение `' OR '1'='1`:
```
SELECT * FROM users WHERE username = '' OR '1'='1'
```
База вернёт всех пользователей. Или передаёт `'; DROP TABLE users; --`:
```
SELECT * FROM users WHERE username = ''; DROP TABLE users; --'
```

```
// НЕПРАВИЛЬНО — конкатенация строк
query := "SELECT * FROM users WHERE username = '" + username + "'"
// ПРАВИЛЬНО — параметры, драйвер экранирует автоматически
row := db.QueryRow("SELECT * FROM users WHERE username = $1", username)
// ПРАВИЛЬНО — с несколькими параметрами
row := db.QueryRow(
   "SELECT * FROM users WHERE username = $1 AND password = $2",
   username, password,
)
```
**Дополнительные меры**
**Least privilege** — пользователь БД должен иметь только нужные права. Если приложение только читает — только `SELECT`, без `DROP`, `DELETE`.
Никогда не подставлять пользовательский ввод в SQL через конкатенацию строк.

271Как у вас фича проходит от начала до прода?
Middle
HR
**Типичный цикл доставки фичи:**
**1. Постановка задачи.** PM или заказчик описывает требования. Разработчики участвуют в груминге: уточняют, декомпозируют, оценивают. Задача ведётся в **GitLab Issues** с лейблами и milestone.
**2. Дизайн / планирование.** Для сложных задач — технический дизайн-документ или обсуждение в команде. Для простых — сразу в работу.
**3. Разработка.** Ветка от `main`, реализация, саморевью перед открытием **Merge Request**. При создании MR и каждом обновлении автоматически прогоняются **юнит-тесты** в GitLab CI. Также поднимается **отдельное окружение под фиче-ветку** для изолированного тестирования.
**4. Code Review.** Минимум один апрув. Замечания → правки → повторный просмотр. Всё в интерфейсе GitLab MR.
**5. QA / тестирование.** Автотесты в **GitLab CI/CD**, при необходимости — ручное тестирование на фиче-окружении или **staging**. Staging — отдельная ветка и окружение для интеграционных тестов.
**6. Деплой.** Merge в `main` → деплой на staging → smoke-тест → деплой в **production**. По нажатию кнопки в GitLab CI (`when: manual`) можно раскатать последнюю версию из нужной ветки на нужное окружение.
**7. Наблюдение после деплоя.** Смотрим метрики, ошибки в логах, алерты 15–30 минут после релиза.
**Инструменты:** GitLab Issues → GitLab MR → GitLab CI/CD → Kubernetes.
Пример: «От груминга до прода у нас обычно 2–5 дней для небольшой фичи. Крупные фичи прячем за feature flag и раскатываем постепенно.»

273В чем ты видишь разницу между tech lead и team lead?
